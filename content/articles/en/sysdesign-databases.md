# Databases

Database selection is one of the most consequential architectural decisions you can make. It determines your consistency model, query patterns, operational complexity, and how much you will suffer during migrations three years from now. This article covers the SQL vs NoSQL trade-off, the positioning of PostgreSQL, MongoDB, and Redis, replication and partitioning strategies, Go connection pooling, and migration management.

## SQL vs NoSQL

### SQL (Relational Databases)

Relational databases organise data into tables with rows and columns. They enforce a schema, support JOIN operations, and provide ACID transaction guarantees.

**ACID:**
- **Atomicity:** a transaction is all-or-nothing.
- **Consistency:** a transaction brings the database from one valid state to another.
- **Isolation:** concurrent transactions appear to execute serially.
- **Durability:** committed transactions survive crashes.

**Best suited for:**
- Structured data with clear relationships (users, orders, products).
- Workloads that require multi-row or multi-table transactions.
- Complex queries with JOINs, aggregations, and filtering.
- Systems where data integrity constraints are business requirements (foreign keys, unique constraints, check constraints).

**Popular choices in Go:** PostgreSQL (the default), MySQL, CockroachDB (distributed SQL), SQLite (embedded/testing).

### NoSQL (Non-Relational Databases)

NoSQL is an umbrella term for databases that do not use the relational model. They trade off some SQL guarantees for flexibility, horizontal scalability, or specialised performance.

**Categories:**

| Type | Examples | Strengths |
|---|---|---|
| Document | MongoDB, CouchDB | Flexible schema, nested data, fast single-document operations |
| Key-Value | Redis, DynamoDB | Sub-millisecond access, simple data model |
| Wide-Column | Cassandra, BigTable | Write-heavy, time-series, massive scale |
| Graph | Neo4j, Amazon Neptune | Relationship-heavy queries (social graphs, recommendations) |
| Time-Series | InfluxDB, TimescaleDB | High-frequency timestamped data (metrics, telemetry) |

**When to choose NoSQL:**
- Schema changes frequently or is unknown upfront (document store).
- Horizontal scalability is a hard requirement from day one (Cassandra, DynamoDB).
- Access pattern is always by primary key or secondary index, never by arbitrary queries (key-value).
- You are building a graph-traversal-heavy feature (graph DB).

**The default advice:** start with PostgreSQL. It supports JSON columns (`jsonb`), full-text search, and arrays — giving you significant NoSQL-like flexibility within a relational model. Add specialised databases only when PostgreSQL is demonstrably insufficient for a specific workload.

## PostgreSQL in Go

The canonical Go library for PostgreSQL is `jackc/pgx` (v5), which is faster and more feature-rich than the older `lib/pq`.

```go
import (
    "github.com/jackc/pgx/v5/pgxpool"
)

// Connection pool — share across your application
pool, err := pgxpool.New(ctx, os.Getenv("DATABASE_URL"))
if err != nil {
    log.Fatal(err)
}
defer pool.Close()

// Configured pool
config, _ := pgxpool.ParseConfig(os.Getenv("DATABASE_URL"))
config.MaxConns = 20
config.MinConns = 2
config.MaxConnLifetime = 30 * time.Minute
config.MaxConnIdleTime = 5 * time.Minute
pool, _ = pgxpool.NewWithConfig(ctx, config)

// Query with automatic scanning
rows, err := pool.Query(ctx, "SELECT id, email FROM users WHERE active = $1", true)
users, err := pgx.CollectRows(rows, pgx.RowToStructByName[User])

// Transaction
tx, err := pool.Begin(ctx)
if err != nil {
    return err
}
defer tx.Rollback(ctx) // no-op after Commit

_, err = tx.Exec(ctx, "UPDATE accounts SET balance = balance - $1 WHERE id = $2", amount, fromID)
if err != nil {
    return err
}
_, err = tx.Exec(ctx, "UPDATE accounts SET balance = balance + $1 WHERE id = $2", amount, toID)
if err != nil {
    return err
}
return tx.Commit(ctx)
```

For applications with complex SQL and type safety requirements, use `sqlc` — it generates type-safe Go code from SQL queries at build time:

```sql
-- query.sql
-- name: GetUser :one
SELECT id, email, created_at FROM users WHERE id = $1;
```

```go
// Generated by sqlc — fully type-safe
user, err := queries.GetUser(ctx, userID)
```

## MongoDB in Go

MongoDB stores documents (BSON, essentially JSON with types) in collections. The official Go driver is `go.mongodb.org/mongo-driver/v2`.

```go
import (
    "go.mongodb.org/mongo-driver/v2/bson"
    "go.mongodb.org/mongo-driver/v2/mongo"
    "go.mongodb.org/mongo-driver/v2/mongo/options"
)

client, err := mongo.Connect(options.Client().ApplyURI(os.Getenv("MONGODB_URI")))
defer client.Disconnect(ctx)

coll := client.Database("mydb").Collection("users")

// Insert
result, err := coll.InsertOne(ctx, bson.D{
    {Key: "email", Value: "alice@example.com"},
    {Key: "active", Value: true},
})

// Find with filter
var user User
err = coll.FindOne(ctx, bson.D{{Key: "_id", Value: userID}}).Decode(&user)

// Aggregation pipeline
pipeline := mongo.Pipeline{
    {{Key: "$match", Value: bson.D{{Key: "active", Value: true}}}},
    {{Key: "$group", Value: bson.D{
        {Key: "_id", Value: "$country"},
        {Key: "count", Value: bson.D{{Key: "$sum", Value: 1}}},
    }}},
    {{Key: "$sort", Value: bson.D{{Key: "count", Value: -1}}}},
}
cursor, err := coll.Aggregate(ctx, pipeline)
```

**MongoDB's strengths in practice:**
- Documents map directly to application objects — no ORM impedance mismatch.
- Flexible schema: add new fields without migrations.
- Embedded arrays and nested documents for 1:N relationships without JOINs.
- Horizontal sharding built into the core (since version 1).

**MongoDB's weaknesses:**
- Multi-document transactions are supported (since v4.0) but expensive.
- No foreign key constraints — referential integrity is the application's responsibility.
- Aggregation pipelines are verbose compared to SQL.

## Redis as a Database

Redis is most often used as a cache, but it is also a legitimate primary database for specific workloads:

- **Session storage:** low-latency reads, built-in TTL per key.
- **Rate limiting:** atomic `INCR` + `EXPIRE` per time window.
- **Leaderboards:** sorted sets with O(log N) rank operations.
- **Real-time counters and statistics:** atomic increment operations.
- **Pub/sub messaging:** lightweight fan-out without persistent consumers.

For durability, Redis supports **RDB snapshots** (point-in-time dump) and **AOF (Append-Only File)** logging. With `appendfsync always`, Redis is durable to single-command granularity, at the cost of throughput.

```go
// Rate limiting with Redis
func (s *Service) CheckRateLimit(ctx context.Context, userID string) (bool, error) {
    key := fmt.Sprintf("ratelimit:%s:%d", userID, time.Now().Unix()/60)
    
    pipe := s.rdb.Pipeline()
    incr := pipe.Incr(ctx, key)
    pipe.Expire(ctx, key, time.Minute)
    _, err := pipe.Exec(ctx)
    if err != nil {
        return false, err
    }
    
    return incr.Val() <= 100, nil // 100 requests per minute
}
```

## Replication

Replication copies data from a primary (write) node to one or more replica (read) nodes.

**Purposes:**
- **High availability:** if the primary fails, a replica is promoted.
- **Read scaling:** route read queries to replicas to reduce load on the primary.
- **Disaster recovery:** replicas in different availability zones or regions.

### Synchronous vs Asynchronous Replication

| Mode | Behaviour | Trade-off |
|---|---|---|
| Synchronous | Primary waits for at least one replica to confirm before returning | Zero data loss, higher write latency |
| Asynchronous | Primary returns as soon as it writes locally | Lower write latency, replication lag = potential data loss |

PostgreSQL uses synchronous replication with `synchronous_commit = on` (can be set per transaction). Most deployments use asynchronous replication with a manually-triggered failover via Patroni or similar.

### Read Replicas in Go

```go
// Use a dedicated read replica connection for SELECT queries
type DB struct {
    primary *pgxpool.Pool
    replica *pgxpool.Pool
}

func (db *DB) QueryUser(ctx context.Context, id int64) (*User, error) {
    // Read from replica — may be slightly stale
    rows, err := db.replica.Query(ctx, "SELECT * FROM users WHERE id = $1", id)
    // ...
}

func (db *DB) CreateUser(ctx context.Context, u *User) error {
    // Write to primary
    _, err := db.primary.Exec(ctx, "INSERT INTO users ...")
    return err
}
```

**Warning:** after a write, always read back from the primary for data the writer immediately needs. Reading from a replica immediately after a write can return stale data.

## Partitioning

Database partitioning (also called "table partitioning") splits a large table into smaller physical chunks based on a partition key, while presenting a single logical table to the application.

**Horizontal partitioning (sharding):** rows are split across multiple databases. See the Scalability article for details.

**PostgreSQL table partitioning** (same machine, multiple table files):

```sql
-- Range partitioning by date
CREATE TABLE events (
    id          BIGINT,
    created_at  TIMESTAMPTZ NOT NULL,
    payload     JSONB
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2025 PARTITION OF events
    FOR VALUES FROM ('2025-01-01') TO ('2026-01-01');

CREATE TABLE events_2026 PARTITION OF events
    FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');

-- PostgreSQL automatically routes inserts and prunes partitions in queries
SELECT * FROM events WHERE created_at >= '2026-01-01'; -- only scans events_2026
```

Benefits: faster queries (partition pruning), easier bulk deletion of old data, parallel query across partitions.

## Connection Pooling in Go

Database connections are expensive: each holds a socket, server memory, and (for PostgreSQL) a backend process. A Go service with 100 goroutines should not open 100 database connections simultaneously — the database will be overwhelmed.

### pgxpool

`pgxpool` manages a pool of connections internally. Configure it based on your PostgreSQL `max_connections` setting and the number of application instances.

```go
config, _ := pgxpool.ParseConfig(os.Getenv("DATABASE_URL"))

// Sizing heuristic: max_connections in PostgreSQL / number of app instances
// e.g., postgres max_connections=100, 5 app instances → MaxConns = 20
config.MaxConns = 20
config.MinConns = 2                    // keep warm connections
config.MaxConnLifetime = 30 * time.Minute
config.MaxConnIdleTime = 5 * time.Minute
config.HealthCheckPeriod = time.Minute

// BeforeAcquire hook — useful for setting session parameters
config.BeforeAcquire = func(ctx context.Context, conn *pgx.Conn) bool {
    // Return false to discard the connection
    return true
}

pool, err := pgxpool.NewWithConfig(ctx, config)
```

### PgBouncer

For applications with very many short-lived connections (serverless, many replicas), use **PgBouncer** as a connection pooler in front of PostgreSQL. PgBouncer maintains a small number of real PostgreSQL connections and multiplexes hundreds of application connections onto them.

Modes:
- **Session pooling:** one PostgreSQL connection per client session (default).
- **Transaction pooling:** one PostgreSQL connection per transaction — highest efficiency, but incompatible with prepared statements and some PostgreSQL features.

## Migration Strategy

### Principles

1. **Every schema change is a migration** — version-controlled, tested, and applied in a known order.
2. **Migrations must be backwards compatible** during deployment. In a rolling deployment, both old and new application code run simultaneously against the same database.
3. **Separate deployment from schema change** for destructive operations (dropping columns, renaming tables).

### Expand-Contract Pattern

For zero-downtime migrations:

1. **Expand:** add the new column/table alongside the old one. Old code ignores it.
2. **Deploy new code** that writes to both old and new, reads from old.
3. **Backfill** existing rows to populate the new column.
4. **Deploy again:** read from new column, write to new only.
5. **Contract:** drop the old column/table in a separate migration.

### Go Migration Tools

**golang-migrate** is the most widely used migration tool in Go:

```bash
migrate -path ./migrations -database "$DATABASE_URL" up
migrate -path ./migrations -database "$DATABASE_URL" down 1
```

```go
// Embedded migrations
import "github.com/golang-migrate/migrate/v4"
import _ "github.com/golang-migrate/migrate/v4/source/iofs"

//go:embed migrations/*.sql
var migrationsFS embed.FS

func runMigrations(dbURL string) error {
    sourceDriver, err := iofs.New(migrationsFS, "migrations")
    if err != nil {
        return err
    }
    m, err := migrate.NewWithSourceInstance("iofs", sourceDriver, dbURL)
    if err != nil {
        return err
    }
    return m.Up()
}
```

Migration files follow a `{version}_{description}.{up|down}.sql` naming convention:
```
migrations/
  001_create_users.up.sql
  001_create_users.down.sql
  002_add_email_index.up.sql
  002_add_email_index.down.sql
```

**Atlas** (`ariga.io/atlas`) is a more modern alternative that can generate migrations from Go struct definitions and validates that migrations are backwards compatible.

## Self-Check Questions

1. **You need to store user profiles that frequently gain new optional fields. Should you use PostgreSQL or MongoDB, and why?**
   *Both work, but PostgreSQL's `jsonb` column lets you store flexible data alongside structured fields, preserving ACID and SQL query capability. Use MongoDB if the entire document is schemaless and you never need relational constraints.*

2. **Your PostgreSQL primary has asynchronous replicas. You update a user's email and immediately redirect them to their profile page, which reads from a replica. The user sees the old email. What pattern prevents this?**
   *Read-your-writes: route the read immediately after the write to the primary, or use a replication token that the replica must catch up to before serving the read.*

3. **What is the difference between database replication and partitioning?**
   *Replication creates copies of the same data on multiple nodes (for HA and read scaling). Partitioning splits data across nodes or table files so that each shard holds a distinct subset (for write scaling and query pruning).*

4. **Why should connection pool MaxConns be a function of the number of application instances?**
   *Each instance opens up to MaxConns connections. If you run 10 instances with MaxConns=50, you potentially open 500 connections to PostgreSQL, which may exceed its `max_connections` limit and cause connection rejection.*
