# Очереди сообщений

Очереди сообщений — связующее звено распределённых систем. Они отделяют системы, порождающие события, от систем, их потребляющих, сглаживают всплески трафика, обеспечивают повторные попытки при сбоях и формируют основу событийно-управляемых и микросервисных архитектур.

Эта статья охватывает три наиболее распространённые очередные системы в экосистеме Go — Kafka, NATS и RabbitMQ — и архитектурные паттерны, построенные поверх них: pub/sub, event sourcing, CQRS и различные семантики доставки, определяющие поведение при сбоях.

## Зачем очереди?

Без очереди сервис A обращается к сервису B синхронно:

```
Клиент → Сервис A → Сервис B
```

Если сервис B медленный, клиент ждёт. Если сервис B недоступен, запрос падает. При пике трафика сервис B перегружается.

С очередью:

```
Клиент → Сервис A → Очередь → Сервис B (асинхронно)
```

Сервис A записывает сообщение и сразу возвращает ответ. Сервис B обрабатывает его, когда готов. Очередь буферизует пики, обеспечивает долговечность при недоступности сервиса B и разделяет циклы деплоя.

**Когда использовать очереди:**
- Нагрузки с высоким потреблением CPU или I/O (отправка email, обработка изображений, генерация отчётов).
- Рабочие процессы, охватывающие несколько сервисов, где каждый шаг может завершиться независимым сбоем.
- Паттерны fanout, где одно событие должно запустить несколько независимых действий.
- Журналы аудита и event sourcing, где важны порядок и долговечность событий.

**Когда НЕ использовать очереди:**
- Вызывающий ожидает синхронного ответа (использовать HTTP/gRPC).
- Нужны строгие ACID-транзакции между сообщением и базой данных (рассмотреть паттерн transactional outbox).
- Операционные накладные расходы превышают выгоду — для небольшой команды PostgreSQL LISTEN/NOTIFY может заменить полноценный Kafka.

## Kafka

Kafka — распределённый лог. Он дописывает события в партиционированные реплицированные логи (топики) и хранит их в течение настраиваемого периода. Потребители читают события по позиции (offset) и могут воспроизвести их с любого момента.

**Основные понятия:**
- **Топик:** именованный поток событий, партиционированный по брокерам.
- **Партиция:** упорядоченный, неизменяемый сегмент лога. У топика может быть 1–1000 партиций; больше партиций = больше параллелизма, но больше накладных расходов.
- **Offset:** позиция сообщения внутри партиции. Потребители отслеживают собственный offset; Kafka не удаляет сообщения при потреблении.
- **Consumer group:** несколько потребителей в группе читают отдельные партиции — параллельное потребление с упорядоченностью внутри каждой партиции.

**Гарантия доставки:** по умолчанию **at-least-once**. С `acks=all` (продюсер) + идемпотентный потребитель достигается **exactly-once** в рамках одного кластера (через транзакции).

**Лучше всего подходит для:**
- Высокопроизводительных потоков событий (миллионы событий/сек).
- Воспроизведения событий и event sourcing — потребители могут перемотать на любой offset.
- Журналов аудита, хранящихся неделями или месяцами.
- Потоковой обработки с Kafka Streams или Apache Flink.

**Go-клиент:** `github.com/segmentio/kafka-go` или `github.com/confluentinc/confluent-kafka-go`.

```go
import "github.com/segmentio/kafka-go"

// Продюсер
writer := &kafka.Writer{
    Addr:                   kafka.TCP("localhost:9092"),
    Topic:                  "user-events",
    Balancer:               &kafka.LeastBytes{},
    RequiredAcks:           kafka.RequireAll, // acks=all
    AllowAutoTopicCreation: true,
}
defer writer.Close()

err := writer.WriteMessages(ctx,
    kafka.Message{
        Key:   []byte(userID),
        Value: eventJSON,
    },
)

// Потребитель
reader := kafka.NewReader(kafka.ReaderConfig{
    Brokers:  []string{"localhost:9092"},
    GroupID:  "notification-service",
    Topic:    "user-events",
    MinBytes: 10e3, // 10 KB
    MaxBytes: 10e6, // 10 MB
})
defer reader.Close()

for {
    msg, err := reader.ReadMessage(ctx)
    if err != nil {
        break
    }
    processEvent(msg.Value)
    // Offset коммитится автоматически при ReadMessage
    // Используйте FetchMessage + CommitMessages для ручного управления
}
```

## NATS

NATS — лёгкая высокопроизводительная система обмена сообщениями для cloud-native и edge-деплоев. Проще и быстрее Kafka, но с более слабыми гарантиями долговечности по умолчанию.

**Основные понятия:**
- **Subject:** строка вида `orders.created` или `user.>` (wildcard). Нет партиций — любой подписчик, совпадающий с subject, получает сообщение.
- **Core NATS:** fire-and-forget, только в памяти. Сообщения, не доставленные подписчику, теряются.
- **NATS JetStream:** персистентные, долговечные потоки поверх Core NATS с настраиваемым хранением, воспроизведением и at-least-once доставкой.

**Гарантии доставки:**
- Core NATS: **at-most-once** (если подписчик офлайн, сообщение теряется).
- JetStream: **at-least-once** с подтверждениями; **exactly-once** с окном дедупликации.

**Лучше всего подходит для:**
- Реального времени с низкой задержкой (телеметрия IoT, синхронизация состояния в играх, живые уведомления).
- Коммуникации в service mesh как альтернатива gRPC для внутренних сервисов.
- Нагрузок, допускающих потерю сообщений (метрики, heartbeat мониторинга).
- Небольших команд, которым нужны низкие операционные расходы (NATS — один бинарник без требований к Zookeeper).

**Go-клиент:** `github.com/nats-io/nats.go`.

```go
import "github.com/nats-io/nats.go"

nc, _ := nats.Connect("nats://localhost:4222")
defer nc.Drain()

// Публикация (fire-and-forget)
nc.Publish("orders.created", orderJSON)

// Подписка
nc.Subscribe("orders.*", func(msg *nats.Msg) {
    fmt.Printf("Получено на %s: %s\n", msg.Subject, msg.Data)
})

// JetStream — с долговечностью и подтверждением
js, _ := nc.JetStream()
js.Publish("ORDERS.created", orderJSON)

sub, _ := js.Subscribe("ORDERS.*", func(msg *nats.Msg) {
    process(msg.Data)
    msg.Ack() // ручное подтверждение
}, nats.Durable("order-processor"), nats.ManualAck())
```

## RabbitMQ

RabbitMQ — традиционный брокер сообщений на основе протокола AMQP. Моделирует коммуникацию через **exchange** и **очереди**: продюсеры публикуют в exchange, который маршрутизирует сообщения в очереди по ключам маршрутизации и правилам привязки.

**Основные понятия:**
- **Типы exchange:** `direct` (точное совпадение), `topic` (шаблонное с `.` и `*`/`#`), `fanout` (широковещание), `headers` (маршрутизация по метаданным).
- **Очередь:** место ожидания сообщений. Может быть долговечной (переживает перезапуск), эксклюзивной (один потребитель) и автоудаляемой.
- **Binding:** правило связи exchange с очередью, опционально с ключом маршрутизации.
- **Подтверждения:** потребитель отправляет `ack` по завершении обработки. При отключении без ack сообщение возвращается в очередь.

**Гарантия доставки:** **at-least-once** при ручных ack. Exactly-once требует идемпотентных потребителей.

**Лучше всего подходит для:**
- Сложной логики маршрутизации (по типу, приоритету, тенанту и т.д.).
- Задач с требованием exactly-once visibility (через эксклюзивных потребителей).
- Традиционного распределения задач через очередь (паттерн пула воркеров).
- Интероперабельности протоколов — AMQP хорошо поддерживается во всех языках.

**Go-клиент:** `github.com/rabbitmq/amqp091-go`.

```go
import amqp "github.com/rabbitmq/amqp091-go"

conn, _ := amqp.Dial("amqp://guest:guest@localhost:5672/")
ch, _ := conn.Channel()
defer ch.Close()

// Объявление очереди
q, _ := ch.QueueDeclare("task_queue", true, false, false, false, nil)

// Публикация
ch.Publish("", q.Name, false, false, amqp.Publishing{
    DeliveryMode: amqp.Persistent, // переживает перезапуск брокера
    ContentType:  "application/json",
    Body:         taskJSON,
})

// Потребление
msgs, _ := ch.Consume(q.Name, "", false, false, false, false, nil)
for msg := range msgs {
    processTask(msg.Body)
    msg.Ack(false) // ручное подтверждение
}
```

## Когда что выбирать

| Критерий | Kafka | NATS (JetStream) | RabbitMQ |
|---|---|---|---|
| Пропускная способность | Очень высокая (млн/с) | Высокая (десятки тысяч/с) | Средняя (тысячи/с) |
| Задержка | 5–15 мс | < 1 мс | 1–5 мс |
| Хранение и воспроизведение | Да (недели/месяцы) | Да (настраивается) | Нет (потреблено → удалено) |
| Семантика доставки | At-least-once / exactly-once | At-most-once / at-least-once | At-least-once |
| Маршрутизация | Топик + партиция | Subject (wildcard) | Exchange + ключ маршрутизации |
| Операционная сложность | Высокая (Kafka + Zookeeper/KRaft) | Низкая (один бинарник) | Средняя (UI управления включён) |
| Лучше всего для | Event sourcing, журнал аудита, аналитика | IoT, realtime, mesh микросервисов | Очереди задач, сложная маршрутизация |

## Паттерн Pub/Sub

В pub/sub (publish/subscribe) издатели отправляют сообщения в топик, не зная, кто их получит. Подписчики регистрируют интерес к топику и получают все совпадающие сообщения.

```
Издатель A ──┐
              ├──► Топик: "order.created" ──► Подписчик 1 (сервис склада)
Издатель B ──┘                           ──► Подписчик 2 (сервис уведомлений)
                                         ──► Подписчик 3 (сервис аналитики)
```

Развязка двунаправленная: издатели не знают о подписчиках; подписчики не знают, кто публикует. Добавление нового потребителя не требует никаких изменений у издателя.

В Go с NATS:

```go
// Издатель — не знает, кто слушает
nc.Publish("order.created", orderJSON)

// Несколько независимых подписчиков
nc.Subscribe("order.created", inventoryHandler)
nc.Subscribe("order.created", notificationHandler)
nc.Subscribe("order.created", analyticsHandler)
```

## Event Sourcing

Event sourcing — архитектурный паттерн, при котором состояние сущности полностью выводится из упорядоченного лога событий, а не из хранения только текущего состояния.

```
Вместо:                    Хранить:
таблица orders             таблица events (только дополнение)
─────────────              ─────────────────────────────────────────────
id: 42                     id: 1, order_id: 42, type: OrderCreated,    data: {...}
status: shipped            id: 2, order_id: 42, type: PaymentReceived, data: {...}
items: [...]               id: 3, order_id: 42, type: OrderShipped,    data: {...}
```

**Преимущества:**
- Полный журнал аудита — известно, что произошло и когда.
- Временные запросы — восстановление состояния на любой момент времени.
- Воспроизведение — переобработка всех событий с новой логикой (полезно для исправления ошибок и новых функций).
- Естественная совместимость с событийными архитектурами.

**Недостатки:**
- Чтение текущего состояния требует воспроизведения всех событий (смягчается снимками).
- Эволюция схемы для старых событий затруднена.
- Не подходит для всех предметных областей — простой CRUD-инвентарь не получит заметной выгоды.

Event sourcing и Kafka — естественная пара: хранение Kafka и воспроизведение по offset напрямую соответствуют семантике лога событий.

## CQRS (Command Query Responsibility Segregation)

CQRS разделяет операции записи (команды) и чтения (запросы), используя разные модели, нередко разные базы данных.

```
                ┌─ Сторона команд ─┐
Клиент ──запись──► Обработчик команд → БД записи (PostgreSQL, события)
                └──────────────────┘
                          │ публикует события
                          ▼
                ┌─ Сторона запросов ──────┐
Клиент ──чтение──► Обработчик запросов ← БД чтения (Redis, Elasticsearch, денормализованная)
                └─────────────────────────┘
```

Модель запросов обновляется асинхронно через потребление событий со стороны команд. Её можно оптимизировать отдельно для производительности чтения (например, полностью денормализованный Elasticsearch-индекс), не влияя на производительность записи.

CQRS наиболее ценен, когда:
- Профили нагрузки чтения и записи сильно различаются.
- Нужно несколько представлений для чтения одних данных (для разных API-клиентов).
- Модель записи сложная (event sourcing), а модель чтения должна быть простой.

## Семантики доставки

### At-Most-Once (максимум один раз)

Сообщение доставляется ноль или один раз. Если сеть теряет подтверждение, повтора нет.

- **Допустимо когда:** метрики, телеметрия, реал-тайм уведомления, где потеря сообщения лучше дублирующей обработки.
- **По умолчанию в:** Core NATS, UDP-системах.

### At-Least-Once (минимум один раз)

Сообщение доставляется один или более раз. При потере подтверждения брокер повторяет попытку до получения подтверждения.

- **Следствие:** возможны дублирующиеся сообщения. Потребители должны быть **идемпотентными** — обработка одного сообщения дважды даёт тот же результат.
- **По умолчанию в:** Kafka (с acks), RabbitMQ (с acks), NATS JetStream.

Идемпотентность в Go:

```go
func processOrder(ctx context.Context, orderID string) error {
    // Проверка идемпотентности: это уже обрабатывалось?
    exists, err := db.ExistsProcessedOrder(ctx, orderID)
    if err != nil {
        return err
    }
    if exists {
        return nil // уже обработано — безопасно пропустить
    }

    // Атомарная обработка с записью идемпотентности
    return db.WithTx(ctx, func(tx *sql.Tx) error {
        if err := fulfillOrder(ctx, tx, orderID); err != nil {
            return err
        }
        return markOrderProcessed(ctx, tx, orderID)
    })
}
```

### Exactly-Once (ровно один раз)

Сообщение доставляется и обрабатывается ровно один раз, даже при повторах и сбоях.

- **Как:** идемпотентность на стороне продюсера (Kafka присваивает порядковый номер; дубликаты отбрасываются) + транзакционные коммиты на стороне потребителя (транзакции Kafka или идемпотентные потребители с дедупликацией).
- **Стоимость:** значительные накладные расходы — транзакции, двухфазные фиксации, более высокая задержка.
- **Когда использовать:** финансовые транзакции, биллинг, изменения инвентаря, где дубликаты причиняют реальный бизнес-ущерб.

## Dead Letter Queue

Dead letter queue (DLQ) — отдельная очередь, принимающая сообщения, которые не удалось обработать после N попыток.

```go
// RabbitMQ — настройка DLQ при объявлении очереди
args := amqp.Table{
    "x-dead-letter-exchange":    "dlx",
    "x-dead-letter-routing-key": "dead",
    "x-message-ttl":             int32(5000), // повтор через 5 сек
    "x-max-retries":             int32(3),
}
ch.QueueDeclare("task_queue", true, false, false, false, args)

// После 3 неудачных попыток RabbitMQ автоматически направляет в DLQ
```

DLQ обеспечивает:
- **Видимость:** dead-lettered сообщения можно инспектировать и отлаживать.
- **Алертинг:** рост DLQ выше порога должен триггерить алерт.
- **Переобработку:** после исправления ошибки сообщения можно воспроизвести из DLQ.

В Kafka DLQ — это соглашение (обычно топик `<topic>-dlt`), реализованное в потребителе:

```go
func consumeWithDLQ(ctx context.Context, msg kafka.Message) {
    const maxRetries = 3

    for attempt := range maxRetries {
        if err := processMessage(ctx, msg); err != nil {
            if attempt == maxRetries-1 {
                // Публикация в DLQ
                dlqWriter.WriteMessages(ctx, kafka.Message{
                    Key:   msg.Key,
                    Value: msg.Value,
                    Headers: []kafka.Header{
                        {Key: "error", Value: []byte(err.Error())},
                        {Key: "original-topic", Value: []byte(msg.Topic)},
                    },
                })
            }
            time.Sleep(backoff(attempt))
            continue
        }
        return
    }
}

func backoff(attempt int) time.Duration {
    return time.Duration(math.Pow(2, float64(attempt))) * time.Second
}
```

## Вопросы для самопроверки

1. **Сервис заказов публикует событие "заказ создан". Три downstream-сервиса потребляют его: склад, уведомления и аналитика. Должны ли они использовать одну общую consumer group или три отдельные? Почему?**
   *Три отдельные consumer group. У каждой группы собственная позиция offset и она обрабатывает каждое сообщение независимо. Общая группа разделит сообщения между потребителями — каждое сообщение попадёт только к одному из трёх.*

2. **В чём разница между at-least-once и exactly-once доставкой? Что должен реализовывать потребитель для безопасной обработки at-least-once?**
   *At-least-once: сообщения могут дублироваться при повторах. Exactly-once: обработка ровно один раз даже при сбоях. Для at-least-once: потребители должны быть идемпотентными (проверять, было ли сообщение уже обработано; пропускать или сливать при дубликате).*

3. **Опишите паттерн transactional outbox. Какую проблему он решает?**
   *Сервис записывает бизнес-событие в таблицу "outbox" в той же транзакции базы данных, что и бизнес-данные. Отдельный поллер читает outbox и публикует в очередь. Это гарантирует атомарность записи в БД и публикации сообщения — решая проблему dual-write.*

4. **Когда вы выберете RabbitMQ вместо Kafka для очереди задач?**
   *Когда нужна сложная маршрутизация каждого сообщения (по типу, тенанту, приоритету), когда сообщения должны удаляться после обработки (долгосрочное хранение не нужно), или когда операционная простота важнее пропускной способности и возможности воспроизведения.*
