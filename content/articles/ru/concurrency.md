# Конкурентность в Go

Конкурентность — одна из главных причин, по которым Go стал популярным языком для бэкенда. Встроенная модель горутин и каналов позволяет писать параллельные программы без тяжёлых абстракций потоков или коллбэков. Для собеседований это означает, что данную тему проверяют почти всегда: от базовых вопросов «чем горутина отличается от потока ОС» до практических задач на дедлоки и утечки.

## Зачем это нужно

Go создавался для разработки серверного ПО, где конкурентность — норма жизни: HTTP-запросы приходят одновременно, обращения к базе данных нужно делать параллельно, а фоновые задачи должны не блокировать основной поток. Вместо того чтобы добавлять потоки на уровне ОС (дорого — несколько МБ стека каждый), Go запускает горутины — лёгкие сопрограммы с начальным стеком около 8 КБ, управляемые планировщиком Go.

На собеседовании конкурентность появляется в трёх форматах:
1. **Теоретические вопросы** — модель памяти, happens-before, планировщик M:N.
2. **Разбор кода** — «что выведет эта программа», «есть ли здесь data race».
3. **Практические задачи** — реализовать пул воркеров, graceful shutdown, rate limiter.

Знание всех четырёх слоёв конкурентности — горутин, каналов, пакета `sync` и `context` — позволяет уверенно закрыть любой из этих форматов.

## Горутины — основа конкурентности

Горутина запускается через ключевое слово `go` перед вызовом функции. Планировщик Go (GOMAXPROCS потоков ОС) распределяет горутины по доступным ядрам без участия программиста.

```go
go func() {
    fmt.Println("привет из горутины")
}()
```

Для ожидания завершения группы горутин Go 1.25 предоставляет `sync/errgroup` c методом `wg.Go()`, который автоматически перехватывает панику и возвращает первую возникшую ошибку:

```go
import "golang.org/x/sync/errgroup"

g, ctx := errgroup.WithContext(context.Background())

for i := range 5 {
    i := i // до 1.22 нужно было захватывать переменную; с 1.22+ цикловая переменная уникальна
    g.Go(func() error {
        return processItem(ctx, i)
    })
}

if err := g.Wait(); err != nil {
    log.Fatal(err)
}
```

Подробнее о горутинах, планировщике и распространённых паттернах — в отдельной статье **«Горутины»**.

## Каналы — коммуникация между горутинами

Каналы — типизированные очереди для передачи данных между горутинами. Философия Go: «не общайтесь через общую память — делитесь памятью через коммуникацию».

```go
ch := make(chan int, 1) // буферизованный канал ёмкостью 1

ch <- 42       // отправка
v := <-ch      // получение
```

Небуферизованный канал синхронизирует отправителя и получателя (отправка блокирует до получения). Буферизованный канал допускает до N сообщений в полёте без блокировки отправителя.

Каналы используются для:
- **pipeline** — цепочка стадий обработки данных;
- **fan-out / fan-in** — распределение работы и сбор результатов;
- **done-канал** — сигнал завершения без `context` (устаревший паттерн, сейчас предпочтительнее `context.WithCancel`).

Подробнее — в статье **«Каналы»**.

## Пакет sync — низкоуровневые примитивы

Когда канал избыточен или нужна тонкая защита разделяемого состояния, используют пакет `sync`.

**`sync.Mutex` / `sync.RWMutex`** — защищают критическую секцию. `RWMutex` позволяет нескольким читателям работать одновременно при эксклюзивной записи.

```go
var mu sync.Mutex
counter := 0

mu.Lock()
counter++
mu.Unlock()
```

**`sync.WaitGroup`** — ждёт завершения N горутин. Классический паттерн `Add(1) + go + Done()` всё ещё применяется, когда errgroup не нужен.

**`sync.Once`** — выполняет функцию ровно один раз, даже при конкурентных вызовах. Идеально для ленивой инициализации:

```go
var once sync.Once
var instance *MyService

func getInstance() *MyService {
    once.Do(func() {
        instance = &MyService{}
    })
    return instance
}
```

**`sync.Map`** — конкурентно-безопасная карта. Подходит для сценариев «много читателей, редкие записи»; для частых записей обычный `map + Mutex` быстрее.

**`sync/atomic`** — атомарные операции над числами и указателями без мьютексов. Используются в hot path, где мьютекс создаёт слишком много накладных расходов.

Подробнее — в статье **«Пакет sync»**.

## Context — управление жизненным циклом

`context.Context` — стандартный способ передавать сигнал отмены, дедлайн и произвольные значения через цепочку вызовов. Каждый API в стандартной библиотеке Go, который делает I/O, принимает `context.Context` первым аргументом.

```go
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel() // всегда освобождайте ресурсы

resp, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
```

Три ключевых конструктора:
- `context.WithCancel` — ручная отмена через вызов `cancel()`.
- `context.WithTimeout` — автоматическая отмена через заданный интервал.
- `context.WithDeadline` — автоматическая отмена в конкретный момент времени.

Контекст нужно передавать явно, первым аргументом — никогда не хранить в структурах. Дочерние контексты автоматически отменяются при отмене родительского.

Подробнее — в статье **«Context»**.

## Типичные ошибки на собеседованиях

**1. Утечка горутины.** Горутина заблокирована на канале или операции, которая никогда не завершится. Программа растёт по памяти. Решение: всегда предусматривать `done`-сигнал или использовать `context`.

```go
// Плохо: горутина зависнет навсегда, если никто не читает из ch
go func() {
    ch <- result // утечка, если получатель ушёл
}()

// Хорошо: отмена через context
go func() {
    select {
    case ch <- result:
    case <-ctx.Done():
    }
}()
```

**2. Data race на разделяемой переменной.** Одновременная запись и чтение одной переменной из нескольких горутин — неопределённое поведение. Запускайте тесты с флагом `-race`, чтобы обнаруживать такие места автоматически.

**3. Дедлок.** Две горутины ждут друг друга. Классический пример — отправка в небуферизованный канал без получателя. Go runtime обнаруживает полный дедлок и паникует с `all goroutines are asleep`.

**4. Захват переменной цикла (до Go 1.22).** Все горутины, запущенные в цикле, ссылались на одну и ту же переменную `i`. Начиная с Go 1.22, каждая итерация цикла создаёт отдельную переменную — проблема исчезла.

**5. Игнорирование `cancel()`.** `context.WithCancel` и `context.WithTimeout` возвращают функцию `cancel`. Если не вызвать её, дочерний контекст остаётся живым, пока не завершится родительский — это утечка ресурсов. `defer cancel()` сразу после создания контекста — обязательный паттерн.

## Что дальше

Эта статья — обзор. Каждый раздел разбирается подробно в отдельных материалах:

- **Горутины** — планировщик M:N, GOMAXPROCS, паттерны worker pool и pipeline.
- **Каналы** — буферизованные vs небуферизованные, `select`, направленные каналы, распространённые паттерны.
- **Пакет sync** — Mutex, RWMutex, WaitGroup, Once, Map, atomic.
- **Context** — дерево контекстов, propagation, хранение значений, best practices.

Рекомендуемый порядок изучения: горутины → каналы → sync → context. После этого практикуйте комбинированные задачи: graceful shutdown сервера, rate limiter, semaphore через каналы.
