# SQL для Go-разработчика

SQL — язык, которому более пятидесяти лет, и он по-прежнему остаётся обязательным на любом бэкенд-собеседовании. Go-разработчику часто кажется, что достаточно знать пакет `database/sql`, но интервьюеры проверяют понимание самого языка запросов: индексов, транзакций, планов выполнения и паттернов, которые определяют производительность системы.

## Почему SQL важен для Go-разработчиков

Большинство Go-сервисов хранят данные в PostgreSQL или MySQL. ORM в Go намеренно минималистичны (GORM, sqlc, sqlx), а многие команды предпочитают сырой SQL — из соображений читаемости и предсказуемости производительности. Это значит, что разработчик должен понимать, что именно происходит в базе данных, а не скрываться за магией ORM.

На собеседованиях SQL встречается в трёх форматах:

1. **Теоретические вопросы** — «что такое ACID», «какие уровни изоляции существуют», «как работают B-tree индексы».
2. **Написание запросов** — JOIN-ы, оконные функции, CTE, агрегации.
3. **Анализ производительности** — чтение EXPLAIN ANALYZE, обнаружение N+1, выбор индексов.

## Основы реляционной модели

В реляционной базе данные организованы в **таблицы** (relations) из строк и столбцов. Каждая строка уникальна благодаря **первичному ключу** (PRIMARY KEY). Связи между таблицами устанавливаются через **внешние ключи** (FOREIGN KEY).

Три нормальные формы, о которых чаще всего спрашивают:

- **1НФ** — атомарность значений, нет повторяющихся групп столбцов.
- **2НФ** — 1НФ + каждый неключевой атрибут полностью зависит от первичного ключа.
- **3НФ** — 2НФ + нет транзитивных зависимостей между неключевыми атрибутами.

Нормализация уменьшает аномалии обновления, но иногда денормализация оправдана ради производительности чтения.

## Основные типы запросов

### SELECT и фильтрация

Базовый синтаксис неизменен, но важно понимать порядок выполнения:

```sql
SELECT department, COUNT(*) AS headcount
FROM   employees
WHERE  salary > 80000
GROUP  BY department
HAVING COUNT(*) > 5
ORDER  BY headcount DESC
LIMIT  10;
```

Порядок выполнения (логический): `FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT`. Это объясняет, почему нельзя использовать псевдоним из `SELECT` в `WHERE`.

### JOIN

JOIN — объединение строк из двух таблиц по условию. Четыре основных вида:

- **INNER JOIN** — только строки, у которых есть совпадение в обеих таблицах.
- **LEFT JOIN** — все строки левой таблицы + совпадающие строки правой (NULL если нет совпадения).
- **RIGHT JOIN** — зеркало LEFT JOIN.
- **FULL OUTER JOIN** — все строки обеих таблиц.

```sql
SELECT u.name, o.total
FROM   users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE  o.created_at > NOW() - INTERVAL '30 days';
```

### Агрегации и GROUP BY

Агрегатные функции (`COUNT`, `SUM`, `AVG`, `MAX`, `MIN`) сворачивают группы строк в одно значение. Фильтрация результатов агрегации делается через `HAVING`, а не `WHERE`.

## Индексы — ключ к производительности

Индекс — это отдельная структура данных (обычно B-tree), которая позволяет базе данных находить строки без полного сканирования таблицы. Без индекса любой `WHERE id = 42` превращается в sequential scan по всей таблице.

Основные виды индексов в PostgreSQL:

- **B-tree** (по умолчанию) — для операций `=`, `<`, `>`, `BETWEEN`, `LIKE 'prefix%'`.
- **Hash** — только для `=`, чуть быстрее B-tree для точного поиска.
- **GIN** — для составных типов: массивы, JSONB, полнотекстовый поиск.
- **GiST** — для геометрических типов и range-типов.

Важно знать, когда индекс **не помогает**: использование функции над индексированным столбцом (`WHERE LOWER(email) = ...`), низкая селективность (столбец с двумя значениями), маленькая таблица.

## Транзакции и ACID

Транзакция — группа операций, выполняемых атомарно. ACID — гарантии, которые база предоставляет для транзакций:

- **Atomicity** — либо все операции, либо ни одной.
- **Consistency** — транзакция переводит базу из одного корректного состояния в другое.
- **Isolation** — параллельные транзакции не видят промежуточных результатов друг друга (в зависимости от уровня изоляции).
- **Durability** — зафиксированные данные сохранятся даже при сбое.

Уровни изоляции SQL (от слабого к сильному): Read Uncommitted, Read Committed, Repeatable Read, Serializable. PostgreSQL по умолчанию использует Read Committed.

## Пакет database/sql в Go

Стандартный пакет `database/sql` предоставляет абстракцию над любым драйвером:

```go
import (
    "context"
    "database/sql"
    _ "github.com/lib/pq" // регистрирует драйвер PostgreSQL
)

db, err := sql.Open("postgres", dsn)
if err != nil {
    return err
}
defer db.Close()

// Настройка пула соединений
db.SetMaxOpenConns(25)
db.SetMaxIdleConns(5)
db.SetConnMaxLifetime(5 * time.Minute)
```

`sql.DB` — это пул соединений, а не одно соединение. Go 1.25 гарантирует потокобезопасность пула: можно безопасно использовать один `*sql.DB` из разных горутин.

Основные методы:

- `db.QueryContext` — выборка множества строк.
- `db.QueryRowContext` — выборка одной строки.
- `db.ExecContext` — INSERT/UPDATE/DELETE без возврата строк.
- `db.BeginTx` — начало транзакции.
- `db.PrepareContext` — подготовленный запрос.
