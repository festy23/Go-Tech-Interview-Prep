# TCP/IP

TCP/IP — фундамент, на котором работает весь интернет. Для Go-разработчика это не абстрактная теория: каждый `http.Client`, каждое `net.Dial` создаёт TCP-соединение. Понимание handshake, TIME_WAIT, алгоритма Нейгла и управления перегрузкой напрямую влияет на производительность и надёжность сервисов. Разбираем стек снизу вверх: от модели OSI до конкретных настроек в Go.

## Модель OSI и где в ней живёт Go

Модель OSI (7 уровней) — концептуальный фреймворк для понимания сетевых протоколов. Для Go-разработчика актуальны четыре:

| Уровень | Номер | Протоколы | Go-абстракция |
|---------|-------|-----------|---------------|
| Прикладной | 7 | HTTP, gRPC, DNS | `net/http`, `google.golang.org/grpc` |
| Транспортный | 4 | TCP, UDP | `net.Conn`, `net.PacketConn` |
| Сетевой | 3 | IP, ICMP | `net.IP` |
| Канальный | 2 | Ethernet, Wi-Fi | Недоступен из Go напрямую |

Пакет `net` в Go работает на 3–4 уровне. `net/http` — на 7 уровне поверх TCP. Понимание, на каком уровне происходит проблема (DNS-ошибка? потеря пакета? ошибка приложения?), — ключевой навык для диагностики.

## TCP: гарантированная доставка

TCP (Transmission Control Protocol) обеспечивает:
- **Надёжность**: потерянные пакеты ретрансмитируются.
- **Порядок**: байты доставляются в том же порядке, в каком отправлены.
- **Управление потоком**: получатель сообщает об объёме буфера (window size).
- **Управление перегрузкой**: отправитель адаптируется к пропускной способности сети.

Цена — latency. Каждый сегмент требует подтверждения (ACK). Установка соединения занимает один RTT (round-trip time) для handshake.

## TCP Three-Way Handshake

Установка TCP-соединения — **трёхэтапное рукопожатие**:

```
Клиент                      Сервер
  |                            |
  |------- SYN (seq=x) ------->|  Клиент хочет подключиться
  |                            |
  |<-- SYN-ACK (seq=y,ack=x+1)-|  Сервер подтверждает, сообщает свой seq
  |                            |
  |------- ACK (ack=y+1) ----->|  Клиент подтверждает сервер
  |                            |
  |========= Данные ===========|  Соединение установлено
```

**SYN (Synchronize)**: клиент выбирает начальный sequence number (ISN) — случайное число для безопасности — и отправляет его серверу.

**SYN-ACK**: сервер подтверждает ISN клиента (`ack = x + 1`) и сообщает свой ISN (`seq = y`).

**ACK**: клиент подтверждает ISN сервера (`ack = y + 1`). Соединение установлено.

Итого: **1 RTT** до начала передачи данных. При высоких задержках (inter-continent) это ощутимо — поэтому TLS 1.3 оптимизирует handshake, а HTTP/2 мультиплексирует запросы через одно соединение.

### Что проверяется на собеседовании

Типичный вопрос: «Что произойдёт, если SYN пакет дропнется?» — клиент повторит SYN через exponential backoff (1 с, 2 с, 4 с...), до тайм-аута соединения.

## Закрытие соединения и TIME_WAIT

TCP-соединение закрывается через **четырёхэтапный процесс**:

```
Клиент                      Сервер
  |                            |
  |--------- FIN ------------->|  Клиент закончил отправку
  |<-------- ACK --------------|  Сервер подтверждает
  |                            |  (сервер ещё может отправлять данные)
  |<-------- FIN --------------|  Сервер закончил отправку
  |--------- ACK ------------->|  Клиент подтверждает
  |                            |
[TIME_WAIT: 2*MSL]              |  Соединение закрыто
```

### TIME_WAIT

После отправки последнего ACK инициатор закрытия переходит в состояние `TIME_WAIT` на **2×MSL** (Maximum Segment Lifetime, обычно 60 секунд).

Зачем? Два случая:
1. Последний ACK может потеряться → сервер перешлёт FIN → клиент должен быть ещё жив, чтобы ответить.
2. «Блуждающие» пакеты от старого соединения не должны интерпретироваться как данные нового соединения с теми же адресами и портами.

### Проблема TIME_WAIT

При высокой нагрузке (нагрузочное тестирование, HTTP-клиент без keep-alive) одна машина создаёт тысячи соединений. Каждое после закрытия занимает порт на 60 секунд. Эфемерных портов у Linux ~28 000 (диапазон `ip_local_port_range`). При исчерпании новые соединения не устанавливаются.

```bash
# Диагностика
ss -s | grep TIME-WAIT

# Смотрим распределение состояний
ss -tan | awk '{print $1}' | sort | uniq -c | sort -rn
```

**Решения**:
- Включить keep-alive: переиспользовать соединения вместо постоянного открытия/закрытия.
- `net.ipv4.tcp_tw_reuse = 1`: разрешить переиспользование TIME_WAIT сокетов для исходящих соединений (безопасно).
- `SO_LINGER` с timeout=0: немедленный RST вместо FIN (небезопасно для приложений, только для тестирования).

## Алгоритм Нейгла

**Алгоритм Нейгла** (Nagle's Algorithm) уменьшает количество пакетов, объединяя мелкие данные:

> Пока есть неподтверждённые данные в сети, не отправляй мелкий пакет — жди, пока не наберётся MSS байт или не придёт все ACK.

MSS (Maximum Segment Size) — обычно 1460 байт для Ethernet (MTU 1500 − 20 IP − 20 TCP).

**Когда алгоритм полезен**: для bulk transfer (большие файлы) он снижает overhead от tiny packets.

**Когда алгоритм вреден**: для интерактивных протоколов (SSH, базы данных) задержка в несколько миллисекунд раздражает. Например, при отправке 3 байт без алгоритма Нейгла они немедленно отправляются. С алгоритмом — буферизуются до ACK предыдущего пакета.

### Отключение в Go

```go
conn, err := net.Dial("tcp", "localhost:5432")
if err != nil {
    return err
}
tcpConn := conn.(*net.TCPConn)
tcpConn.SetNoDelay(true) // TCP_NODELAY — отключает алгоритм Нейгла
```

`http.Transport` в Go устанавливает `TCP_NODELAY` по умолчанию. Для большинства Go-сервисов ничего делать не нужно.

## TCP Window и управление потоком

TCP использует **скользящее окно** для управления потоком:

- **Receive window (rwnd)**: получатель сообщает, сколько байт он готов принять в буфер.
- Отправитель не может отправить больше данных, чем `min(cwnd, rwnd)`.
- При заполнении буфера получатель уменьшает `rwnd` вплоть до 0 (zero window) — отправитель останавливается.

```
Seq: 1000        1500        2000        2500
     [data1      ][data2     ][data3     ]
     |------- window = 1500 байт --------|
     ^                                   ^
  последний ACK               последний ACK + rwnd
```

**Window scaling** (RFC 1323): позволяет увеличить окно до 1 ГБ. Без него максимум — 65 535 байт, что при RTT 100 мс даёт пропускную способность всего ~5 Мбит/с.

## Управление перегрузкой

В отличие от управления потоком (буфер получателя), **управление перегрузкой** контролирует нагрузку на сеть.

Отправитель поддерживает **congestion window (cwnd)** — количество байт, которые можно отправить без ACK.

### Фазы

**Slow Start**: начинаем с cwnd = 1 MSS. После каждого ACK cwnd удваивается (exponential growth). Продолжается до порога `ssthresh` или потери пакета.

```
Round 1: cwnd = 1 MSS  → 1 пакет
Round 2: cwnd = 2 MSS  → 2 пакета
Round 3: cwnd = 4 MSS  → 4 пакета
Round 4: cwnd = 8 MSS  → 8 пакетов
...до ssthresh или потери
```

**Congestion Avoidance**: после достижения `ssthresh` cwnd растёт линейно (+1 MSS за RTT).

**Fast Retransmit**: при получении 3 дублированных ACK (пакет потерян) — немедленная ретрансмиссия без ожидания timeout.

**Fast Recovery**: после fast retransmit cwnd = ssthresh + 3 MSS (не сбрасывается в 1, как при timeout).

### Алгоритмы

- **CUBIC**: стандарт в Linux. Рост cwnd по кубической функции от времени последней потери.
- **BBR** (Bottleneck Bandwidth and RTT): Google's algorithm. Моделирует реальную пропускную способность и задержку, не реагирует на единичные потери.

Для высокоскоростных интернет-соединений BBR работает значительно лучше CUBIC.

## UDP vs TCP

| Характеристика | TCP | UDP |
|----------------|-----|-----|
| Надёжность | Гарантирована | Нет |
| Порядок | Гарантирован | Нет |
| Установка соединения | 3-way handshake | Нет |
| Управление потоком | Да | Нет |
| Управление перегрузкой | Да | Нет |
| Overhead | Высокий | Минимальный |
| Latency | Выше | Ниже |
| Использование | HTTP, SMTP, FTP | DNS, VoIP, игры, QUIC |

**Когда UDP:** приложения, где устаревшие данные хуже потерянных (видеостриминг, VoIP), или где есть собственная логика ретрансмиссии (QUIC, DTLS).

**TCP в Go**: весь `net/http` использует TCP. `net.Listen("tcp", ":8080")`, `net.Dial("tcp", ...)`.

**UDP в Go**: `net.ListenPacket("udp", ":53")`, `net.Dial("udp", "8.8.8.8:53")`.

## TCP в Go: практика

### Базовый TCP-сервер

```go
package main

import (
    "bufio"
    "fmt"
    "log/slog"
    "net"
)

func main() {
    ln, err := net.Listen("tcp", ":8080")
    if err != nil {
        slog.Error("listen failed", "err", err)
        return
    }
    defer ln.Close()

    slog.Info("listening", "addr", ln.Addr())

    for {
        conn, err := ln.Accept()
        if err != nil {
            slog.Error("accept failed", "err", err)
            continue
        }
        go handleConn(conn)
    }
}

func handleConn(conn net.Conn) {
    defer conn.Close()

    scanner := bufio.NewScanner(conn)
    for scanner.Scan() {
        line := scanner.Text()
        fmt.Fprintf(conn, "echo: %s\n", line)
    }
    if err := scanner.Err(); err != nil {
        slog.Error("scan error", "err", err)
    }
}
```

### Таймауты на TCP-соединении

```go
conn, err := net.DialTimeout("tcp", "example.com:80", 5*time.Second)
if err != nil {
    return err
}

// Дедлайн для чтения/записи
conn.SetDeadline(time.Now().Add(10 * time.Second))

// Только для чтения
conn.SetReadDeadline(time.Now().Add(5 * time.Second))

// Только для записи
conn.SetWriteDeadline(time.Now().Add(5 * time.Second))
```

Важно: дедлайн — абсолютное время, не duration. Устанавливайте его перед каждой операцией чтения/записи, а не один раз при создании соединения.

### Keep-Alive в Go

```go
dialer := &net.Dialer{
    Timeout:   30 * time.Second,
    KeepAlive: 30 * time.Second, // отправляет TCP keep-alive каждые 30 сек
}

conn, err := dialer.DialContext(ctx, "tcp", "example.com:80")
```

`http.Transport` по умолчанию включает keep-alive с интервалом 15 секунд.

### Диагностика TCP в Linux

```bash
# Все TCP-соединения Go-процесса (PID 12345)
ss -tnp | grep pid=12345

# Счётчики ретрансмиссий, ошибок TCP
netstat -s | grep -E "retransmit|failed"

# Перехват пакетов на порту 8080
tcpdump -i any -n 'port 8080' -w dump.pcap

# Анализ pcap
tcpdump -r dump.pcap -A

# Статистика TIME_WAIT
ss -s | head -5
```

## Типичные вопросы на собеседованиях

**Почему TIME_WAIT существует именно 2×MSL?** MSL — максимальное время жизни сегмента в сети (обычно 30 или 60 секунд). 2×MSL гарантирует, что все «блуждающие» пакеты от старого соединения успеют истечь до создания нового соединения с теми же параметрами.

**Что такое SYN flood?** Атака, при которой атакующий отправляет много SYN-пакетов без завершения handshake. Сервер хранит полуоткрытые соединения в очереди (backlog). Контрмера — SYN cookies: сервер кодирует состояние в sequence number и не хранит состояние до ACK.

**Чем TCP отличается от UDP?** TCP гарантирует надёжность, порядок и управление перегрузкой ценой latency и overhead. UDP — нет гарантий, минимальный overhead. UDP используется там, где latency критична или есть собственная логика надёжности (QUIC, DNS, VoIP).

**Что такое Nagle's algorithm и когда его отключать?** Объединяет мелкие пакеты для снижения overhead. Отключать (`TCP_NODELAY`) для интерактивных протоколов, где задержка критична: базы данных, SSH, игровые серверы.

**Что происходит при переполнении receive buffer?** Получатель устанавливает rwnd = 0 (zero window). Отправитель останавливает отправку и периодически посылает window probe, пока получатель не освободит буфер.

**Как работает fast retransmit?** При получении 3 одинаковых ACK (дубликаты) — один пакет потерян, но последующие дошли. Не ждём timeout, немедленно ретрансмитируем потерянный сегмент.
