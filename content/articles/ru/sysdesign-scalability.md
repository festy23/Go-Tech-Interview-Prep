# Масштабируемость

Масштабируемость — способность системы выдерживать растущую нагрузку за счёт добавления ресурсов. Это один из первых вопросов на каждом системном интервью, потому что практически каждое архитектурное решение имеет последствия для масштабируемости: где хранить состояние, как маршрутизировать запросы, как партиционировать данные.

## Вертикальное и горизонтальное масштабирование

### Вертикальное масштабирование (Scale Up)

Добавить больше CPU, ОЗУ или более быстрые диски на существующей машине. База данных, обрабатывающая 500 запросов/сек на 4-ядерном сервере, может потянуть 2000 запросов/сек на 16-ядерном без изменений в коде.

**Преимущества:**
- Просто — никаких изменений в приложении или топологии деплоя.
- Нет сложности распределённых систем (нет шардирования, нет сетевых разделов).
- Стабильные гарантии строгой консистентности (одна машина, одна база данных).

**Недостатки:**
- Жёсткий предел: у железа есть потолок. Крупнейший инстанс AWS (u-24tb1.metal) имеет 224 vCPU и 24 ТБ ОЗУ — впечатляет, но конечно.
- Единая точка отказа — при падении машины вся система недоступна.
- Стоимость единицы производительности нелинейно растёт на верхнем конце.

### Горизонтальное масштабирование (Scale Out)

Добавить больше машин и распределить нагрузку между ними. Уровень веб-серверов вырастает с 2 до 20 экземпляров; уровень базы данных использует репликацию и шардирование.

**Преимущества:**
- Нет жёсткого потолка — добавляйте машины сколько угодно.
- Отказоустойчивость: потеря одной из двадцати машин восстановима.
- Экономичность: много commodity-машин дешевле одной огромной.

**Недостатки:**
- Состояние нужно выносить наружу или реплицировать: запрос, попавший на сервер A, должен иметь доступ к данным, которые предыдущий запрос записал на сервере B.
- Сложность распределённых систем: сетевые разделы, задержка репликации, split-brain.
- Операционные накладные расходы: больше машин для мониторинга, патчинга и координации.

### Принцип stateless-сервисов

Ключ к горизонтальному масштабированию — **stateless-сервисы**. Stateless-сервис не хранит в памяти никакого состояния между запросами — ни сессионного, ни пользовательского. Каждый запрос несёт всё необходимое для его обработки, или эта информация хранится во внешнем разделяемом хранилище (база данных, Redis, S3).

```go
// Stateful — нельзя масштабировать горизонтально без sticky sessions
type Handler struct {
    sessions map[string]*Session // in-memory, только на этом экземпляре
}

// Stateless — любой экземпляр может обработать любой запрос
type Handler struct {
    sessionStore SessionStore // Redis, PostgreSQL и т.д.
}

func (h *Handler) ServeHTTP(w http.ResponseWriter, r *http.Request) {
    token := r.Header.Get("Authorization")
    session, err := h.sessionStore.Get(r.Context(), token)
    // ...
}
```

В Go вынести состояние наружу естественно: `database/sql` для PostgreSQL, `go-redis/redis` для Redis, `aws/aws-sdk-go-v2/service/s3` для S3. HTTP-обработчик становится чистой функцией от входных данных и внешнего хранилища.

## Балансировка нагрузки

Балансировщик нагрузки распределяет входящие запросы по пулу бэкенд-серверов. Он разделяет публичный эндпоинт и набор бэкенд-экземпляров, что обеспечивает горизонтальное масштабирование и деплои без простоя.

### Round-Robin

Простейшая стратегия: запросы распределяются по кругу — сервер 1, сервер 2, сервер 3, сервер 1, …

```
Запрос 1 → Сервер A
Запрос 2 → Сервер B
Запрос 3 → Сервер C
Запрос 4 → Сервер A  ← возврат к началу
```

**Подходит, когда:** все бэкенд-серверы одинаковой мощности, а стоимость запросов равномерна.
**Проблема:** не учитывает загрузку серверов — медленный сервер накапливает запросы быстрее, чем обрабатывает.

**Weighted round-robin** присваивает каждому серверу вес, пропорциональный его мощности.

### Consistent Hashing

Consistent hashing — техника распределения запросов (или данных) по изменяемому набору узлов таким образом, чтобы добавление или удаление узла минимизировало перераспределение.

**Алгоритм:**
1. Каждый узел отображается в одну или несколько точек виртуального кольца (хэш идентификатора узла).
2. Каждый входящий ключ (запрос, шард данных) отображается в точку того же кольца.
3. Ключ назначается первому узлу по часовой стрелке от своей позиции на кольце.

```
         Узел A (хэш: 10)
        /
Кольцо: 0 ──── 10 ──── 40 ──── 70 ──── 100
                        \       \
                      Узел B   Узел C
                      (40)     (70)

Хэш ключа = 55 → маршрутизируется на Узел C (следующий по часовой стрелке, позиция 70)
```

**Почему это важно:** при добавлении или удалении узла перераспределяются только ключи в соседней дуге — в среднем `1/N` от общего числа ключей, а не `N-1/N` как при наивном хэшировании по модулю.

**Виртуальные узлы (vnodes):** для улучшения равномерности распределения каждый физический узел представлен несколькими точками на кольце. Это также помогает, когда узлы имеют разную мощность.

Consistent hashing используется в: Cassandra (партиционирование данных), Nginx (выбор upstream), CDN-кэши на граничных узлах, клиентские библиотеки Memcached.

### Другие стратегии

| Стратегия | Описание | Применение |
|---|---|---|
| Наименьшее количество соединений | Маршрутизировать к серверу с наименьшим числом активных соединений | Долгоживущие соединения (WebSocket, gRPC streaming) |
| IP hash | Хэшировать IP-источник к серверу | Sticky sessions, когда серверное состояние неизбежно |
| Случайный | Выбирать случайный сервер | Хорошо работает с большим количеством однородных серверов |
| На основе ресурсов | Маршрутизировать по метрикам CPU/памяти | Гетерогенные кластеры |

## Шардирование

Шардирование — горизонтальное партиционирование базы данных: вместо одной большой таблицы на одном сервере строки распределяются по нескольким базам данных (шардам) на основе ключа шардирования.

### Стратегии шардирования

**Шардирование по диапазону:** разделить пространство ключей на последовательные диапазоны.
- Шард 1: ID пользователей 1–1 000 000
- Шард 2: ID пользователей 1 000 001–2 000 000
- Шард 3: ID пользователей 2 000 001–3 000 000

*Преимущество:* диапазонные запросы эффективны — все данные для ID 500k–600k находятся на шарде 1.
*Недостаток:* горячие точки — если самые активные пользователи самые новые, все записи попадают на шард 3.

**Хэш-шардирование:** применить хэш-функцию к ключу шардирования и сопоставить результат с шардом.

```go
func shardIndex(userID int64, numShards int) int {
    return int(userID % int64(numShards))
}
```

*Преимущество:* равномерное распределение — нет горячих точек.
*Недостаток:* диапазонные запросы дороги (scatter-gather по всем шардам); решардинг при добавлении узлов перемещает ~`(N-1)/N` данных.

**Шардирование по справочнику:** вести таблицу соответствия ключей шардам.
*Преимущество:* максимальная гибкость — любой ключ можно перенести на любой шард.
*Недостаток:* таблица соответствия — узкое место и единая точка отказа.

### Сложности кросс-шардовых операций

Шардирование вводит ограничения, которые легко недооценить:
- **JOIN** между шардами требует scatter-gather на уровне приложения.
- **Транзакции**, охватывающие несколько шардов, нуждаются в распределённых протоколах (2PC, Saga).
- **Глобальные агрегации** (COUNT(*), SUM) требуют слияния частичных результатов.
- **Перебалансировка** при добавлении шардов операционно затратна.

Именно по этим причинам многие системы начинают с одного крупного экземпляра PostgreSQL (с репликами для чтения) и переходят к шардированию только тогда, когда этого уже недостаточно.

## Теорема CAP

Теорема CAP (Брюэр, 2000) утверждает: распределённая система может одновременно гарантировать не более **двух** из трёх свойств:

- **C — Согласованность (Consistency):** каждое чтение возвращает результат последней записи или ошибку.
- **A — Доступность (Availability):** каждый запрос получает (не ошибочный) ответ — но без гарантии актуальности данных.
- **P — Устойчивость к разделению (Partition Tolerance):** система продолжает работать при потере сообщений между узлами.

На практике сетевые разделы неизбежны в любой многоузловой системе (кабели рвутся, коммутаторы теряют пакеты). Поэтому **P — не выбор**, а обязательное условие. Реальный выбор — между **C и A** во время события разделения:

- **CP-системы** (HBase, Zookeeper, etcd): при разделе отказываются отдавать устаревшие данные — возвращают ошибки или становятся недоступными. Правильный ответ, пусть и недоступный.
- **AP-системы** (Cassandra, DynamoDB, CouchDB): при разделе отдают потенциально устаревшие данные вместо ошибок. Доступны, но возможно не консистентны.

Традиционные реляционные СУБД (PostgreSQL, MySQL) обычно являются **CP** при синхронной репликации: они приоритизируют согласованность над доступностью.

**Важный нюанс:** теорема CAP — бинарная, worst-case модель. На практике модель PACELC полезнее: она расширяет CAP, описывая **компромисс между задержкой и согласованностью** в нормальном (без разделения) случае, потому что даже без раздела вы выбираете между синхронной репликацией (меньше доступность/больше задержка) и асинхронной (больше доступность/меньше задержка, но возможны устаревшие чтения).

## Eventual Consistency

Eventual consistency — гарантия живучести: если к данному элементу данных не поступает новых обновлений, все реплики в конечном счёте вернут одинаковое значение.

Это модель консистентности большинства AP-систем. Она слабее *строгой консистентности* (каждое чтение видит последнюю запись), но сильнее *отсутствия консистентности* (произвольное расхождение).

**Паттерны работы с eventual consistency:**

**Read-your-writes consistency:** после того как клиент написал значение, последующие чтения *этим же клиентом* всегда отражают эту запись. Реализуется маршрутизацией чтений клиента на ту же реплику, которая приняла его запись (или проставлением токена на запись, который реплика проверяет перед ответом).

**Монотонные чтения:** если клиент увидел значение версии N, он никогда не увидит значение версии < N. Предотвращает дезориентирующий опыт: прочитал более новую запись, а при обновлении страницы увидел более старую.

**Разрешение конфликтов:** когда две реплики принимают конкурентные записи одного и того же ключа, они в итоге расходятся. Стратегии:
- *Last-write-wins (LWW):* принимать запись с большей меткой времени. Просто, но данные теряются.
- *Векторные часы:* отслеживать причинность — если запись B происходит после записи A, побеждает B; если они конкурентны, показать конфликт для разрешения на уровне приложения.
- *CRDT (Conflict-free Replicated Data Types):* структуры данных с функциями слияния, коммутативными, ассоциативными и идемпотентными — всегда сходятся к одному значению независимо от порядка слияния. Используются в Riak, Redis CRDT и инструментах совместного редактирования.

## Пример: масштабируемый Go-сервис

Типичный Go-микросервис с горизонтальной масштабируемостью:

```go
func main() {
    // 1. Stateless-обработчик — читает из внешнего хранилища
    db, _ := sqlx.Open("pgx", os.Getenv("DATABASE_URL"))
    rdb := redis.NewClient(&redis.Options{Addr: os.Getenv("REDIS_ADDR")})

    handler := &UserHandler{db: db, cache: rdb}

    // 2. Health check для проверок балансировщика
    mux := http.NewServeMux()
    mux.HandleFunc("/health", func(w http.ResponseWriter, _ *http.Request) {
        w.WriteHeader(http.StatusOK)
    })
    mux.Handle("/users/", handler)

    srv := &http.Server{
        Addr:         ":8080",
        Handler:      mux,
        ReadTimeout:  5 * time.Second,
        WriteTimeout: 10 * time.Second,
        IdleTimeout:  120 * time.Second,
    }

    // 3. Graceful shutdown — дождаться завершения текущих запросов
    done := make(chan struct{})
    go func() {
        quit := make(chan os.Signal, 1)
        signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM)
        <-quit

        ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
        defer cancel()
        srv.Shutdown(ctx)
        close(done)
    }()

    srv.ListenAndServe()
    <-done
}
```

Этот сервис разворачивается за любым L7-балансировщиком (Nginx, AWS ALB, Cloudflare). Поскольку он stateless, балансировщик может направлять любой запрос на любой экземпляр, а добавление или удаление экземпляров не требует координации.

## Вопросы для самопроверки

1. **Ваше stateful веб-приложение хранит сессии в локальной памяти. Опишите две стратегии горизонтального масштабирования без изменения кода приложения.**
   *Sticky sessions на балансировщике или перенос хранения сессий в Redis.*

2. **Хэш-шардирование разбивает пользователей по 8 шардам. Нужно добавить 9-й. Какой процент ключей нужно перенести при наивном хэшировании по модулю и при consistent hashing?**
   *По модулю: ~88,9% (8/9 ключей меняют шард). Consistent hashing: ~11,1% (1/9 ключей, только в дуге нового узла).*

3. **По теореме CAP можно ли иметь систему, которая одновременно консистентна и доступна при сетевом разделе?**
   *Нет. Во время раздела нужно выбирать: отдавать потенциально устаревшие данные (AP) или не отвечать до устранения раздела (CP).*

4. **Пользователь публикует новый твит. Через секунду обновляет ленту и не видит его. Какое свойство консистентности нарушено и как это исправить?**
   *Нарушена read-your-writes consistency. Исправление: маршрутизировать последующие чтения пользователя на primary-реплику или использовать токен репликации, который указывает репликам ждать, пока они не догонят запись.*
