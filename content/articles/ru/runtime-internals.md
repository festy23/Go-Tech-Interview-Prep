## Введение

Знание внутреннего устройства ключевых структур данных Go — это то, что отличает разработчика, который «просто использует язык», от того, кто понимает, почему код работает именно так. На собеседованиях эта тема появляется как в явном виде («как устроен map в Go?»), так и косвенно («почему копирование интерфейса не копирует данные?»).

Данная статья разбирает пять структур: **map**, **slice**, **channel**, **interface** и механику **defer/panic/recover**.

## Map: хеш-таблица с бакетами

### Структура hmap

Внутри каждый `map[K]V` в Go — это указатель на структуру `runtime.hmap`:

```go
// Упрощённо, из runtime/map.go
type hmap struct {
    count     int        // количество элементов (len(m))
    flags     uint8
    B         uint8      // log2 числа бакетов: len(buckets) == 2^B
    noverflow  uint16    // приблизительное число overflow-бакетов
    hash0     uint32     // seed для хеш-функции (рандомизация)
    buckets   unsafe.Pointer // массив 2^B бакетов
    oldbuckets unsafe.Pointer // старые бакеты при росте
    nevacuate  uintptr   // прогресс эвакуации при росте
    extra     *mapextra
}
```

### Бакеты (bmap)

Каждый бакет хранит ровно **8 пар ключ-значение**:

```
bmap:
  [tophash: 8 bytes]   — старшие 8 бит хеша каждого ключа
  [keys:    8 * sizeof(K)]
  [values:  8 * sizeof(V)]
  [overflow: *bmap]    — указатель на overflow-бакет
```

`tophash` используется как быстрый фильтр: при поиске сначала сравниваются 8-битные хэши, и только при совпадении — полные ключи. Это снижает число дорогих сравнений.

### Поиск элемента

```
hash := hashfunc(key, m.hash0)
bucket := hash % (1 << m.B)      // индекс бакета
tophash := uint8(hash >> 56)      // старшие 8 бит

for each slot in buckets[bucket] and overflow buckets:
    if tophash[slot] == tophash and keys[slot] == key:
        return &values[slot]
```

### Рост карты (map growth)

Рост происходит в двух случаях:
1. **Load factor > 6.5** (количество элементов / количество бакетов > 6.5) — увеличение размера в 2 раза.
2. **Много overflow-бакетов** — эвакуация (evacuation) для дефрагментации без увеличения размера.

Рост **инкрементальный**: при каждой операции записи эвакуируются 1–2 бакета из `oldbuckets` в `buckets`. Это размазывает стоимость роста по времени — нет «одного большого pause».

```go
// Итерация по map во время роста — безопасна:
// runtime обрабатывает одновременный доступ к старым и новым бакетам
for k, v := range m {
    fmt.Println(k, v)
}
```

### Важные свойства map

- Map **не конкурентно-безопасна** — конкурентная запись вызывает panic.
- Порядок итерации **намеренно рандомизирован** (hash0 — случайное seed при создании).
- Нулевое значение map — `nil`. Чтение из nil map безопасно (возвращает нулевое значение), запись — panic.
- Для конкурентного доступа используйте `sync.Map` или `map + sync.RWMutex`.

## Slice: трёхполевой заголовок

### Структура slice header

Слайс в Go — это не отдельный тип данных, а **заголовок из трёх полей**:

```go
// Из reflect/value.go (упрощённо)
type SliceHeader struct {
    Data uintptr // указатель на базовый массив
    Len  int     // текущая длина
    Cap  int     // ёмкость (от Data до конца массива)
}
```

Это означает, что передача слайса в функцию **копирует заголовок**, но не данные. Функция работает с той же памятью.

```go
func modify(s []int) {
    s[0] = 999 // изменяет оригинальный массив!
}

func main() {
    a := []int{1, 2, 3}
    modify(a)
    fmt.Println(a[0]) // 999
}
```

### append и стратегия роста

`append` добавляет элемент в слайс. Если `len < cap` — просто увеличивает `len`. Если `len == cap` — нужна реаллокация:

```go
// Поведение append:
// 1. len < cap → просто увеличить len, вернуть тот же Data
// 2. len == cap → выделить новый массив, скопировать, вернуть новый заголовок
s := make([]int, 3, 5) // len=3, cap=5
s = append(s, 4)       // len=4, cap=5, тот же массив
s = append(s, 5)       // len=5, cap=5, тот же массив
s = append(s, 6)       // len=6, cap=10 (новый массив!)
```

**Стратегия роста ёмкости** (Go 1.18+, приблизительно):
- до 256 байт: удвоение (×2)
- после 256 байт: рост примерно на 25% + фиксированная добавка

```go
// Из runtime/slice.go (псевдокод):
func growslice(newLen int, oldCap int) int {
    newcap := oldCap
    doublecap := newcap + newcap
    if newLen > doublecap {
        return newLen // если нужно много — взять сколько нужно
    }
    if oldCap < 256 {
        return doublecap // маленькие — удвоить
    }
    for newcap < newLen {
        // постепенное замедление роста: 1.25x + константа
        newcap += (newcap + 3*256) / 4
    }
    return newcap
}
```

### Подводные камни слайсов

**Утечка памяти через sub-slice:**
```go
// Плохо: большой массив остаётся в памяти из-за sub-slice
func getFirst3(big []byte) []byte {
    return big[:3] // Data указывает на тот же массив!
}

// Хорошо: явное копирование
func getFirst3(big []byte) []byte {
    result := make([]byte, 3)
    copy(result, big[:3])
    return result
}
```

**Неожиданное разделение памяти:**
```go
a := []int{1, 2, 3, 4, 5}
b := a[1:3]       // b.Data = &a[1], b.Len=2, b.Cap=4
b = append(b, 99) // ИЗМЕНЯЕТ a[3]! cap позволяет писать в оригинал
fmt.Println(a)    // [1 2 3 99 5] — неожиданно!

// Защита через full slice expression:
b := a[1:3:3] // Cap=2, append создаст новый массив
```

## Channel: hchan и очереди ожидания

### Структура hchan

Каждый канал — указатель на `runtime.hchan`:

```go
// Упрощённо, из runtime/chan.go
type hchan struct {
    qcount   uint          // элементов в буфере
    dataqsiz uint          // ёмкость буфера (cap канала)
    buf      unsafe.Pointer // кольцевой буфер
    elemsize uint16
    closed   uint32
    sendx    uint          // индекс записи в кольцевом буфере
    recvx    uint          // индекс чтения
    recvq    waitq         // очередь заблокированных получателей
    sendq    waitq         // очередь заблокированных отправителей
    lock     mutex
}
```

### sudog — заблокированная горутина

Когда горутина блокируется на отправке или получении, рантайм создаёт `sudog` — структуру, связывающую горутину с каналом:

```go
type sudog struct {
    g    *g            // горутина, которая ждёт
    elem unsafe.Pointer // указатель на данные (отправляемые/принимаемые)
    next *sudog
    prev *sudog
    // ...
}
```

`recvq` и `sendq` — двусвязные списки `sudog`.

### Алгоритм отправки

```
ch <- v:
1. lock(ch.lock)
2. Если канал закрыт → panic
3. Если recvq не пуста → передать v напрямую ждущему получателю (short-circuit), разбудить его
4. Если buf не полон → скопировать v в buf[sendx], sendx++, qcount++
5. Иначе → создать sudog, добавить в sendq, заблокировать горутину
6. unlock(ch.lock)
```

**Прямая передача (direct send)** — оптимизация: если получатель уже ждёт, Go копирует значение напрямую в его стек, минуя буфер. Это быстрее, чем писать в буфер и потом читать.

### Небуферизованный vs буферизованный канал

```go
// Небуферизованный: отправитель и получатель синхронизированы
ch := make(chan int)
go func() { ch <- 1 }() // блокирует до получения
v := <-ch                // разблокирует отправителя

// Буферизованный: до cap элементов без блокировки
ch := make(chan int, 3)
ch <- 1  // не блокирует
ch <- 2  // не блокирует
ch <- 3  // не блокирует
ch <- 4  // блокирует! буфер полон
```

### Закрытие канала

```go
close(ch):
1. lock
2. Если уже закрыт → panic
3. Установить ch.closed = 1
4. Разбудить всех получателей из recvq (получат нулевое значение)
5. Разбудить всех отправителей из sendq (вызовут panic)
6. unlock
```

Правило: только **отправитель** должен закрывать канал. Закрытие — это сигнал «данных больше не будет».

## Interface: iface и eface

### Два типа интерфейсов

**eface** (empty interface) — `any` / `interface{}`:
```go
type eface struct {
    _type *_type         // указатель на метаданные типа
    data  unsafe.Pointer // указатель на данные (или встроенные данные)
}
```

**iface** (non-empty interface) — интерфейс с методами:
```go
type iface struct {
    tab  *itab           // указатель на таблицу методов
    data unsafe.Pointer  // указатель на данные
}
```

### itab — таблица методов

`itab` — это структура, кэширующая связь «конкретный тип + интерфейс»:

```go
type itab struct {
    inter *interfacetype // описание интерфейса
    _type *_type         // конкретный тип
    hash  uint32         // копия _type.hash (для быстрого type switch)
    _     [4]byte
    fun   [1]uintptr     // таблица указателей на методы (variable length!)
}
```

`itab` кэшируется в глобальной хеш-таблице — при повторном приведении типа к интерфейсу поиск в таблице, а не пересоздание.

### Присвоение в интерфейс

```go
var w io.Writer
f := os.Stdout // *os.File

w = f
// w.tab  = itab{inter: io.Writer, type: *os.File, fun: [(*os.File).Write]}
// w.data = unsafe.Pointer(f)
```

**Важно: интерфейс — два слова.** Копирование интерфейса копирует `tab` и `data` (указатели), но не содержимое. Вызов метода через интерфейс — косвенный (через `tab.fun[i]`), что немного дороже прямого вызова.

### nil interface vs nil pointer в интерфейсе

Классическая ловушка:

```go
func returnsError() error {
    var p *MyError = nil
    if false {
        return p // НИКОГДА не возвращайте так!
    }
    return nil
}

err := returnsError()
fmt.Println(err == nil) // false! iface{tab: *MyError, data: nil} != nil interface
```

Интерфейс равен nil только если **оба** поля (`tab` и `data`) равны nil. Интерфейс с ненулевым `tab` (конкретным типом) и нулевым `data` — ненулевой интерфейс.

### Type assertion и type switch

```go
// Type assertion — panic при неверном типе
f := w.(*os.File)

// Безопасная форма — без panic
f, ok := w.(*os.File)

// Type switch — эффективно: использует hash из itab
switch v := i.(type) {
case *os.File:
    // v — *os.File
case *bufio.Writer:
    // v — *bufio.Writer
default:
    // v — исходный тип интерфейса
}
```

## defer / panic / recover

### defer: стек отложенных вызовов

`defer` добавляет вызов функции в «отложенный стек» горутины. Отложенные вызовы выполняются в порядке **LIFO** при выходе из функции — нормальном или через panic.

В Go 1.14+ компилятор оптимизирует «статические» defer (известные на этапе компиляции) через **open-coded defer** — разворачивает их в inline-код без создания структуры `_defer`. Это делает defer почти бесплатным в большинстве случаев.

```go
type _defer struct {
    fn    func()      // отложенная функция
    sp    uintptr     // SP вызывающей функции
    pc    uintptr     // PC возврата
    link  *_defer     // следующий defer в стеке
}
```

```go
func example() {
    defer fmt.Println("third") // выполнится последней
    defer fmt.Println("second")
    defer fmt.Println("first") // выполнится первой (LIFO)
}
// Вывод: first, second, third
```

**defer + именованные возвращаемые значения:**

```go
func readFile(path string) (n int, err error) {
    f, err := os.Open(path)
    if err != nil {
        return
    }
    defer func() {
        if cerr := f.Close(); cerr != nil && err == nil {
            err = cerr // defer может изменить возвращаемое значение!
        }
    }()
    return io.Copy(io.Discard, f)
}
```

### panic: раскрутка стека

`panic(v)` запускает **раскрутку стека** (stack unwinding):
1. Выполняются все defer текущей функции (в порядке LIFO).
2. Горутина «раскручивает» стек вызовов: выполняет defer каждой функции в цепочке.
3. Если panic не перехвачена — программа завершается с goroutine stack dump.

Паника НЕ пересекает границы горутин: если горутина паникует без recover, она убивает всю программу.

```go
func riskyOperation() {
    defer func() {
        if r := recover(); r != nil {
            log.Printf("recovered: %v", r)
        }
    }()

    panic("something went wrong") // эта паника будет перехвачена
}
```

### recover: перехват паники

`recover()` перехватывает текущую панику. Он работает **только внутри defer-функции**. Возвращает значение, переданное в `panic()`.

```go
// recover работает:
defer func() {
    r := recover() // перехватывает панику
}()

// recover НЕ работает (не в defer):
r := recover() // всегда nil, не в defer-контексте

// recover НЕ работает (вложенный вызов):
defer func() {
    innerRecover() // если recover() внутри innerRecover — не перехватит!
}()
```

### Правила panic/recover на собеседованиях

1. `panic` + `recover` — это NOT обычный механизм обработки ошибок. Используйте для действительно исключительных ситуаций.
2. Библиотеки не должны паниковать наружу — перехватывайте паники на границе пакета и возвращайте ошибки.
3. `recover` в одной горутине не перехватывает панику в другой горутине.
4. После `recover` программа продолжает работать, но состояние может быть неконсистентным — будьте осторожны.

```go
// Паттерн: безопасное выполнение пользовательского коллбэка
func safeExecute(fn func() error) (err error) {
    defer func() {
        if r := recover(); r != nil {
            err = fmt.Errorf("panic: %v\n%s", r, debug.Stack())
        }
    }()
    return fn()
}
```

## Сводная таблица: размеры и накладные расходы

| Тип | Размер в памяти | Стоимость копирования |
|-----|-----------------|-----------------------|
| `map[K]V` | 8 байт (указатель на hmap) | Дёшево (копируем указатель) |
| `[]T` | 24 байта (ptr + len + cap) | Дёшево (3 слова) |
| `chan T` | 8 байт (указатель на hchan) | Дёшево (копируем указатель) |
| `interface{}` | 16 байт (tab + data) | Дёшево (2 слова) |
| Вызов через interface | — | +1 indirect (tab lookup) |
| Type assertion | — | Hash сравнение + проверка |

## Вопросы для самопроверки

1. **Почему порядок итерации по map в Go неопределён?**
   При создании map генерируется случайный seed `hash0`. Кроме того, итерация намеренно стартует со случайного бакета — это сделано, чтобы программы не полагались на порядок.

2. **Что произойдёт, если `append` превысит capacity слайса?**
   Будет выделен новый массив большего размера, данные скопированы, возвращён новый заголовок с новым `Data`. Старый заголовок продолжает указывать на старый массив.

3. **Чем небуферизованный канал отличается от буферизованного с точки зрения hchan?**
   У небуферизованного `dataqsiz == 0`, нет буфера. Каждая отправка блокируется до получателя (или передаётся напрямую через short-circuit).

4. **Почему интерфейс с нулевым указателем не равен nil?**
   Интерфейс — пара (tab, data). Если tab != nil (есть конкретный тип), интерфейс ненулевой, даже если data == nil.

5. **В каком порядке выполняются defer? Когда recover перехватывает панику?**
   defer выполняются в порядке LIFO. recover перехватывает панику только если вызван непосредственно внутри defer-функции той горутины, которая паникует.
