# Планировщик и Runtime Go

Runtime Go — это невидимый фундамент каждой программы на Go. Именно он управляет горутинами, сборкой мусора, выделением памяти, работой с сетью и системными вызовами. Разобраться в том, как устроен runtime, значит понять, почему Go-программы работают так, а не иначе: откуда берётся низкая задержка, как удаётся держать сотни тысяч горутин, и почему GC почти не чувствуется на prod.

На собеседованиях уровня senior/staff тема runtime встречается регулярно: интервьюер хочет знать, можете ли вы объяснить поведение своей программы под нагрузкой, правильно ли настроите GOMAXPROCS в контейнере, понимаете ли разницу между stack и heap allocation.

## Что такое runtime Go

В отличие от таких языков, как Java или Python, Go не использует виртуальную машину. Runtime Go компилируется прямо в бинарник вместе с вашим кодом — каждый исполняемый файл Go несёт runtime внутри себя. Это означает отсутствие внешней зависимости при деплое, предсказуемый cold start и полный контроль над поведением программы.

Runtime выполняет несколько ключевых задач:

- **Планирование горутин** — модель GMP (Goroutine / Machine / Processor) мультиплексирует тысячи горутин на небольшое число OS-потоков.
- **Управление памятью** — трёхцветная сборка мусора (tri-color mark-and-sweep) с конкурентными фазами и write barrier.
- **Аллокатор памяти** — иерархия mcache → mcentral → mheap минимизирует блокировки при выделении объектов.
- **Escape analysis** — компилятор определяет, размещать объект на стеке или куче, до того как программа запустится.
- **Netpoll** — интеграция с epoll/kqueue/IOCP для неблокирующего I/O без занятых потоков.
- **Sysmon** — фоновый монитор, следящий за зависшими горутинами, сетевыми таймаутами и форсированной сборкой мусора.

## Планировщик: модель GMP

Центральный элемент runtime — планировщик горутин, реализующий модель **GMP**.

**G (Goroutine)** — структура `runtime.g`, хранящая стек, программный счётчик и статус горутины. Начальный стек — 2–8 КБ, растёт динамически до 1 ГБ.

**M (Machine)** — настоящий OS-поток. M выполняет горутины. При блокирующем системном вызове M отсоединяется от P, а runtime создаёт новый M, чтобы работа не останавливалась.

**P (Processor)** — логический процессор, ресурс планировщика. P хранит локальную очередь горутин (LRQ, до 256 штук) и связывает G с M. Количество P задаётся `GOMAXPROCS`.

```
  P0             P1
  LRQ: G,G,G     LRQ: G,G
     │               │
     M0              M1
     │               │
  OS Thread       OS Thread
```

Когда локальная очередь P пуста, планировщик применяет **work stealing** — забирает половину LRQ другого P. Это выравнивает нагрузку без ручного управления.

```go
import "runtime"

func main() {
    // Количество P, реально используемых планировщиком
    fmt.Println("GOMAXPROCS:", runtime.GOMAXPROCS(0))
    fmt.Println("NumCPU:    ", runtime.NumCPU())
    fmt.Println("Goroutines:", runtime.NumGoroutine())
}
```

Начиная с Go 1.14 планировщик поддерживает **асинхронное вытеснение** через сигнал `SIGURG`: монитор `sysmon` прерывает горутины, работающие дольше ~10 мс, даже если в них нет вызовов функций.

## Garbage Collector: три фазы

Сборщик мусора Go — конкурентный, трёхцветный mark-and-sweep. Цель: минимизировать паузы при сохранении целостности графа объектов.

**Три цвета:**
- **Белый** — объект не посещён, кандидат на удаление.
- **Серый** — объект найден, его потомки ещё не проверены.
- **Чёрный** — объект и все его потомки обработаны, удалению не подлежит.

**Фазы GC:**
1. **Mark setup (STW)** — короткая пауза Stop-The-World: включение write barrier.
2. **Mark (concurrent)** — горутины-маркировщики обходят граф объектов параллельно с работой программы.
3. **Mark termination (STW)** — завершение маркировки, выключение write barrier.
4. **Sweep (concurrent)** — освобождение белых объектов без паузы.

**Write barrier** гарантирует, что мутации указателей во время конкурентной маркировки не нарушат инварианты алгоритма.

Две ключевые переменные окружения:

```bash
GOGC=100        # по умолчанию: запускать GC, когда heap вырастет на 100%
GOMEMLIMIT=512MiB  # Go 1.19+: жёсткий лимит потребления памяти
```

`GOMEMLIMIT` особенно важен в контейнерах — без него runtime может выйти за пределы cgroup и получить OOM Kill от ядра.

## Escape Analysis и аллокатор памяти

**Escape analysis** — статический анализ компилятора, определяющий, куда размещать объект: на стек (дёшево, GC не видит) или на кучу (дороже, GC следит).

```bash
go build -gcflags="-m" ./...
# Вывод: ./main.go:12:6: moved to heap: result
```

Объект «убегает» на кучу, когда:
- возвращается указатель на локальную переменную;
- переменная передаётся в интерфейс;
- размер превышает предел анализа;
- объект захвачен замыканием.

**Иерархия аллокатора:**

| Уровень | Описание | Блокировка |
|---------|----------|-----------|
| mcache  | Per-P кэш span-ов, ~100 классов размеров | Нет |
| mcentral | Глобальный пул span-ов одного класса | Мьютекс на класс |
| mheap  | Куча OS-страниц, treap-структура | Глобальный мьютекс |

Большинство аллокаций small objects обслуживается из mcache без блокировок — именно поэтому Go-программы хорошо масштабируются по ядрам.

## Netpoll: неблокирующий I/O

Go обёртывает epoll (Linux) / kqueue (macOS) / IOCP (Windows) в единый абстрактный слой — **netpoll**. Когда горутина вызывает `net.Conn.Read()` и данных нет, она не блокирует OS-поток, а переходит в состояние ожидания. Sysmon периодически опрашивает netpoll и возвращает готовые горутины в очереди P.

Это позволяет держать миллионы TCP-соединений на небольшом числе OS-потоков.

## Типичные вопросы на собеседованиях

**«Сколько поставить GOMAXPROCS в контейнере с 2 vCPU?»**
По умолчанию Go читает `runtime.NumCPU()`, которое в контейнере может вернуть число ядер хоста, а не квоту cgroup. Используйте библиотеку `uber-go/automaxprocs` или явно задавайте `GOMAXPROCS=2`.

**«Чем отличается GOGC от GOMEMLIMIT?»**
`GOGC` управляет частотой GC через соотношение новой памяти к живой. `GOMEMLIMIT` задаёт абсолютный потолок потребления — GC будет агрессивно работать, чтобы не превысить лимит, даже если это противоречит `GOGC`.

**«Как убедиться, что объект не ускользает на кучу?»**
Запустить `go build -gcflags="-m"` и проанализировать вывод. Переписать код так, чтобы объект не передавался как интерфейс и не захватывался горутиной-замыканием.

**«Что такое STW и насколько долго длятся паузы в современном Go?»**
Stop-The-World возникает дважды за цикл GC (mark setup и mark termination). В Go 1.17+ средняя пауза — доли миллисекунды; типичные prod-значения — 0.1–1 мс.

## Что дальше

Рекомендуемый порядок изучения: **планировщик** → **память** → **внутренняя структура**. Это даст сначала понимание того, как горутины живут, затем — как управляется их память, и наконец — как работают ключевые структуры данных, с которыми вы взаимодействуете каждый день.

После теоретической части переходите к практике: включайте `GODEBUG=schedtrace=1000`, запускайте `go tool pprof` и читайте вывод `go tool trace` — runtime открывается по-настоящему только тогда, когда видишь его в действии на реальных программах.
