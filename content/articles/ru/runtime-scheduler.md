## Введение

Планировщик — это сердце рантайма Go. Именно он отвечает за то, что сотни тысяч горутин «живут» параллельно, не занимая при этом сотни тысяч OS-потоков. В основе лежит кооперативно-вытесняющая модель **GMP** (Goroutine / Machine / Processor) — схема M:N-мультиплексирования, разработанная командой Go ещё в первых версиях языка и последовательно улучшавшаяся.

На собеседованиях планировщик проверяется чаще всего в следующих форматах:
- «Объясните модель GMP» — часто первый вопрос после горутин.
- «Что произойдёт с P, если M заблокируется в системном вызове?»
- «Как правильно выставить GOMAXPROCS в Kubernetes?»
- «Как работает work stealing?»

## Модель GMP в деталях

### G — Goroutine

Горутина описывается структурой `runtime.g` (пакет `runtime`, файл `runtime/runtime2.go`). Ключевые поля:

| Поле | Описание |
|------|----------|
| `stack` | Текущий стековый диапазон `[lo, hi)` |
| `sched` | Сохранённый контекст CPU (PC, SP, …) |
| `atomicstatus` | Атомарный статус: `_Gidle`, `_Grunnable`, `_Grunning`, `_Gwaiting`, … |
| `m` | Указатель на M, на котором горутина сейчас выполняется |
| `goid` | Уникальный идентификатор горутины |

Начальный размер стека — 2–8 КБ (Go 1.25 использует 8 КБ). Стек растёт динамически: при нехватке места рантайм выделяет новый, больший стек, копирует содержимое и обновляет все указатели. Максимум — 1 ГБ (задаётся `runtime/debug.SetMaxStack`).

### M — Machine (OS Thread)

`M` — это реальный поток ОС. Один M всегда привязан к одному P (или ни к какому, если заблокирован). Несколько важных инвариантов:

- Количество M не ограничено; рантайм создаёт новый M, когда все существующие M заняты или заблокированы.
- Существует лимит `GOMAXPROCS` **одновременно работающих** M, но не общего числа M.
- M, который заблокировался в системном вызове (например, в `read(2)`), отсоединяется от P. Когда системный вызов завершается, M пытается захватить свободный P; если P нет — горутина отправляется в глобальную очередь, а M уходит в «парк» (thread cache).

### P — Processor

P — это **ресурс планировщика**, не физический процессор. Он:
- хранит **Local Run Queue** (LRQ) — кольцевой буфер до 256 горутин;
- кэширует объекты mcache (аллокатор памяти);
- при завершении горутины получает новую из своей LRQ или «крадёт» у другого P.

Количество P задаётся `GOMAXPROCS`. По умолчанию — `runtime.NumCPU()`.

```go
package main

import (
    "fmt"
    "runtime"
)

func main() {
    // Текущее значение GOMAXPROCS (0 = только читать, не изменять)
    p := runtime.GOMAXPROCS(0)
    fmt.Println("P:", p)

    // Изменить GOMAXPROCS в рантайме (редко нужно вручную)
    runtime.GOMAXPROCS(2)
    fmt.Println("P after change:", runtime.GOMAXPROCS(0))
}
```

**Когда менять GOMAXPROCS:**
- В контейнерах с квотой CPU < количества ядер хоста — используйте `uber-go/automaxprocs`.
- Для latency-критичных сервисов иногда имеет смысл GOMAXPROCS < NumCPU, чтобы снизить конкуренцию за кэш L3.
- Для CPU-intensive задач (кодирование видео, криптография) — GOMAXPROCS = NumCPU (или чуть меньше, чтобы оставить место ОС).

## Work Stealing

Когда P опустошает свою LRQ, он не простаивает — он ищет работу:

1. Проверяет **GRQ** (Global Run Queue) — забирает `min(len(GRQ)/GOMAXPROCS + 1, 256/2)` горутин.
2. Проверяет **netpoll** — забирает готовые сетевые горутины.
3. **Крадёт у случайного P** — берёт ровно половину его LRQ.
4. Если нигде ничего нет — M переходит в spinning-режим (короткое активное ожидание), затем засыпает.

```
P0 (пустой)              P1
     │                LRQ: G0 G1 G2 G3
     └── steal 50% ──> P1 отдаёт G2, G3
```

Work stealing гарантирует равномерную нагрузку без централизованного диспетчера. Это особенно заметно в воркер-пулах: если один P завален задачами, другие автоматически подхватывают работу.

**Глобальная очередь vs локальная:**
- LRQ — lock-free (P владеет ей единолично).
- GRQ — защищена мьютексом, поэтому обращение к ней дороже.
- Каждые **~61 такт** планировщик принудительно проверяет GRQ (чтобы горутины, попавшие туда из syscall, не «голодали»).

## Sysmon: фоновый монитор

`sysmon` — специальный OS-поток (без P!), запускающийся в отдельном M. Он не нуждается в P, потому что не выполняет горутины, а только мониторит рантайм.

Что делает sysmon каждые 10–20 мс:
1. **Опрашивает netpoll** — переводит готовые I/O-горутины из ожидания в LRQ.
2. **Ретраит syscall** — если M застряло в syscall дольше 20 мкс, отсоединяет P от M.
3. **Вытесняет долгие горутины** — если горутина работает дольше 10 мс, посылает `SIGURG` её M (асинхронное вытеснение, Go 1.14+).
4. **Форсирует GC** — если прошло больше 2 минут с последней сборки мусора, форсирует запуск GC.
5. **Обновляет таймеры** — сигнализирует горутинам, чьи таймеры истекли.

```
sysmon loop:
  every ~10ms:
    - poll netpoll(0) → enqueue ready Gs
    - retake P from blocked syscall Ms
    - preempt long-running Gs (SIGURG)
    - scavenge idle spans (memory to OS)
```

Отключить sysmon нельзя — он неотъемлемая часть планировщика.

## Netpoll: неблокирующий I/O

Netpoll — абстракция над платформенными механизмами асинхронного I/O:
- **Linux**: `epoll_wait`
- **macOS/BSD**: `kqueue`
- **Windows**: IOCP

Когда горутина вызывает `net.Conn.Read()` и данных нет, происходит следующее:
1. Системный вызов возвращает `EAGAIN`.
2. Горутина «паркуется» — переходит в состояние `_Gwaiting`, дескриптор регистрируется в epoll.
3. M освобождается и берёт следующую горутину из LRQ.
4. Когда данные появляются, sysmon (или P при планировании) опрашивает netpoll и переводит горутину в `_Grunnable`.

Это позволяет обслуживать десятки тысяч TCP-соединений на одном OS-потоке — без callback-ов, без async/await, просто прямой синхронный код.

```go
package main

import (
    "fmt"
    "net/http"
    "sync"
)

func main() {
    var wg sync.WaitGroup
    results := make([]int, 100)

    // 100 конкурентных HTTP-запросов: каждая горутина "паркуется" на I/O,
    // не занимая OS-поток.
    for i := range 100 {
        wg.Go(func() { // Go 1.25: wg.Go заменяет wg.Add(1) + go func() + defer wg.Done()
            resp, err := http.Get("https://go.dev")
            if err == nil {
                results[i] = resp.StatusCode
                resp.Body.Close()
            }
        })
    }
    wg.Wait()
    fmt.Println("done, first status:", results[0])
}
```

## Обработка системных вызовов

Системные вызовы — особый случай для планировщика, потому что большинство из них **блокирующие**: пока выполняется `read(2)`, OS-поток заморожен.

Рантайм различает два вида syscall:

**1. «Быстрые» syscall через `entersyscall` / `exitsyscall`**
Для коротких вызовов (< 20 мкс) M остаётся привязанным к P. Если sysmon обнаружит, что syscall затянулся, он ретраит P — отсоединяет P от M и отдаёт его другому M.

**2. CGo и блокирующие вызовы через `entersyscallblock`**
Если известно, что вызов будет длинным, рантайм сразу отпускает P перед вызовом. M блокируется, P подхватывает другой M.

```
M0 (заблокирован в read)      M1 (новый или из парка)
        │                              │
    (нет P)                        P0 (захвачен)
                                   LRQ: G, G, G
```

Когда syscall завершается, M0 пытается захватить P. Если все P заняты — горутина кладётся в GRQ, M0 паркуется.

## Точки кооперации и вытеснение

### Кооперативные точки (Go <1.14)

В ранних версиях планировщик был **чисто кооперативным**: горутина уступала процессор только в заранее известных точках:
- вызов любой функции (пролог функции проверял флаг `preempt`);
- операция с каналом (`ch <- v`, `<-ch`);
- `runtime.Gosched()` — явная уступка;
- `time.Sleep`;
- системный вызов;
- выделение памяти в куче.

Проблема: tight loop без вызовов функций мог заморозить весь P.

### Асинхронное вытеснение (Go 1.14+)

Начиная с Go 1.14 добавлено **асинхронное вытеснение** через `SIGURG`:
1. Sysmon замечает горутину, работающую дольше 10 мс.
2. Посылает `SIGURG` на M.
3. Обработчик сигнала записывает в стек горутины фрейм-заглушку (`asyncPreempt`).
4. Горутина прерывается, её контекст сохраняется, она возвращается в LRQ.

```go
// Этот tight loop НЕ заморозит P в Go 1.14+:
func tightLoop(n int) int {
    sum := 0
    for i := range n {
        sum += i * i // нет вызовов функций, нет точек кооперации
    }
    return sum
}
```

| Механизм | Версии | Описание |
|----------|--------|----------|
| Function call preemption | все | Пролог проверяет флаг preempt |
| Async preemption (SIGURG) | ≥1.14 | Вытесняет любую горутину |
| Syscall preemption | все | M отсоединяется от P автоматически |
| `runtime.Gosched()` | все | Явная уступка CPU |

## Трассировка планировщика: GODEBUG=schedtrace

`GODEBUG=schedtrace=N` выводит статистику планировщика каждые N миллисекунд:

```bash
GODEBUG=schedtrace=1000 go run main.go
```

Пример вывода:
```
SCHED 1000ms: gomaxprocs=8 idleprocs=6 threads=10 spinningthreads=0 idlethreads=3 runqueue=0 [0 0 0 1 0 0 0 0]
```

Расшифровка:
- `gomaxprocs=8` — количество P.
- `idleprocs=6` — P без работы.
- `threads=10` — всего OS-потоков.
- `spinningthreads=0` — M в активном ожидании.
- `runqueue=0` — горутин в GRQ.
- `[0 0 0 1 0 0 0 0]` — размеры LRQ каждого P.

Для детальной трассировки используйте `go tool trace`:

```bash
import "runtime/trace"

func main() {
    f, _ := os.Create("trace.out")
    trace.Start(f)
    defer trace.Stop()
    // ... ваш код
}

// Анализ:
// go tool trace trace.out
```

`go tool trace` показывает визуальную карту горутин, P и M во времени — незаменимо для отладки latency spikes и голодания горутин.

## Частые ошибки и советы

### GOMAXPROCS в контейнерах

```go
// Автоматически выставляет GOMAXPROCS по квоте cgroup
import _ "go.uber.org/automaxprocs"
```

Без этого Go может «думать», что у него 64 ядра, хотя контейнеру выделено 2 vCPU. Результат: избыточный contention и деградация производительности.

### runtime.Gosched() — когда нужен

`runtime.Gosched()` явно уступает CPU текущего P другим горутинам. Используется редко — в основном в tight loops, которые должны быть «вежливыми»:

```go
for {
    if hasWork() {
        doWork()
    } else {
        runtime.Gosched() // дать поработать другим горутинам
    }
}
```

### runtime.LockOSThread() — привязка к потоку

Некоторые C-библиотеки (GUI, OpenGL) требуют, чтобы вызовы шли из одного и того же OS-потока. `runtime.LockOSThread()` гарантирует это:

```go
func runGUI() {
    runtime.LockOSThread()
    defer runtime.UnlockOSThread()
    // Весь GUI-код здесь выполняется строго на одном M
    gui.Init()
    gui.MainLoop()
}
```

## Вопросы для самопроверки

1. **Что такое P в модели GMP? Чем он отличается от M?**
   P — ресурс планировщика (локальная очередь + mcache), M — OS-поток. P связывает G с M; без P M не может выполнять горутины.

2. **Что происходит с P, когда M уходит в долгий системный вызов?**
   Sysmon замечает, что M завис в syscall > 20 мкс, и ретраит P: отсоединяет P от M и отдаёт его другому M (или создаёт новый M).

3. **Как work stealing помогает балансировать нагрузку?**
   Когда LRQ P пуста, P крадёт половину LRQ другого P. Это гарантирует, что ни один P не простаивает, пока у соседей есть работа.

4. **Чем асинхронное вытеснение (Go 1.14+) лучше кооперативного?**
   Кооперативное вытеснение не работает в tight loops без вызовов функций. Асинхронное вытеснение через SIGURG принудительно прерывает любую горутину через ~10 мс, независимо от её содержимого.

5. **Как диагностировать, что горутины «голодают» на конкретном P?**
   `GODEBUG=schedtrace=100` покажет LRQ каждого P. Ненулевые значения в одном P при нулях в остальных — признак несбалансированной нагрузки. `go tool trace` даст визуальную картину.
