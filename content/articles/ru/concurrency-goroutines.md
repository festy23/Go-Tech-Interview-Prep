## Введение

Горутина — это легковесная единица конкурентного выполнения, управляемая рантаймом Go, а **не** операционной системой. Запустить горутину так же просто, как написать `go f()` перед вызовом функции.

Ключевые отличия горутины от потока ОС:

| Характеристика | Горутина | Поток ОС |
|---|---|---|
| Начальный стек | ~2–8 КБ, растёт динамически | ~1–8 МБ, фиксированный |
| Управление | Рантайм Go (user space) | Ядро ОС |
| Переключение контекста | Дёшево, без syscall | Дорого, syscall |
| Лимит | Сотни тысяч | Тысячи |

На практике это значит: вы можете без опасений создать 100 000 горутин — каждая займёт лишь пару килобайт и не заблокирует OS-поток во время ожидания.

## Модель GMP

Планировщик Go реализует модель **GMP** — три сущности, которые взаимодействуют, чтобы эффективно мультиплексировать горутины по потокам ОС (схема **M:N**).

### G — Goroutine (горутина)

Структура `runtime.g` хранит всё состояние горутины: стек, счётчик инструкций, статус (`runnable`, `running`, `waiting`, …). Стек начинается с 2–8 КБ и растёт сегментированно по мере необходимости, вплоть до 1 ГБ (лимит задаётся `runtime/debug.SetMaxStack`).

### M — Machine (поток ОС)

`M` — это реальный поток ОС, созданный рантаймом через `clone(2)` на Linux. `M` выполняет горутины и может блокироваться в системных вызовах. Когда `M` блокируется, рантайм создаёт новый `M`, чтобы не останавливать остальные `P`.

### P — Processor (логический процессор)

`P` — это ресурс планировщика: он связывает `G` с `M` и хранит **локальную очередь горутин** (LRQ, Local Run Queue, до 256 горутин). Количество `P` равно `GOMAXPROCS` (по умолчанию — количество логических ядер CPU).

Глобальная очередь (GRQ, Global Run Queue) используется, когда LRQ переполнена или когда горутина только что создана из системного вызова.

```
 ┌────────────┐   ┌────────────┐
 │    P 0     │   │    P 1     │
 │ LRQ: G,G,G │   │ LRQ: G,G  │
 └─────┬──────┘   └─────┬──────┘
       │                │
       M0               M1
       │                │
    OS Thread        OS Thread
```

**Жизненный цикл горутины:**
1. `go f()` создаёт `G` и кладёт её в LRQ текущего `P` (или в GRQ при переполнении).
2. `P` снимает `G` из своей LRQ и отдаёт `M` для выполнения.
3. Если `G` делает блокирующий системный вызов, `M` отсоединяется от `P`; `P` продолжает работу с другим `M`.
4. Когда системный вызов завершён, горутина возвращается в LRQ ближайшего свободного `P`.

```go
package main

import (
    "fmt"
    "runtime"
)

func main() {
    fmt.Printf("GOMAXPROCS = %d\n", runtime.GOMAXPROCS(0))
    fmt.Printf("NumCPU     = %d\n", runtime.NumCPU())
    fmt.Printf("NumGoroutine = %d\n", runtime.NumGoroutine())
}
```

## Work Stealing

Что происходит, когда один `P` опустошает свою LRQ, а другой завален работой? Планировщик Go применяет алгоритм **work stealing**.

### Алгоритм

1. **Проверить собственную LRQ.** Если пуста — перейти к шагу 2.
2. **Проверить GRQ.** Если есть задачи — взять часть оттуда.
3. **Украсть у другого `P`.** Выбрать случайный `P` и взять **половину** его LRQ.
4. Если нигде ничего нет — `M` переходит в режим ожидания (spinning → sleeping).

```
P0 (пустой) ──steal 50%──> P1 (LRQ: G0,G1,G2,G3)
                                       │
                            P1 отдаёт: G2, G3
```

Work stealing гарантирует, что ни один `P` не простаивает, пока у других есть работа. Это критично для производительности воркер-пулов и пайплайнов.

### Local Run Queue vs Global Run Queue

- **LRQ** обслуживается без блокировок (lock-free) — `P` владеет ей единолично.
- **GRQ** защищена мьютексом — обращение дороже, поэтому используется как буфер второго уровня.
- Каждые ~61 такт планировщик проверяет GRQ, чтобы предотвратить «голодание» горутин, попавших туда (например, из syscall).

## Вытесняющее планирование

### Кооперативная vs вытесняющая многозадачность

В ранних версиях Go (до 1.14) планировщик был **кооперативным**: горутина могла уступить процессор только в точках кооперации — вызовах функций, операциях с каналами, `time.Sleep`, системных вызовах. «Длинная» горутина без единого вызова функции монополизировала поток ОС, мешая всем остальным на том же `P`.

### Асинхронное вытеснение (Go 1.14+)

Начиная с Go 1.14 планировщик поддерживает **асинхронное вытеснение** через сигнал `SIGURG`:

1. Монитор (`sysmon`) каждые ~10 мс сканирует горутины, которые работают дольше 10 мс.
2. Если горутина «застряла», рантайм посылает `SIGURG` потоку `M`.
3. Обработчик сигнала встраивает в стек горутины фрейм-заглушку и возвращает управление планировщику.
4. Горутина будет возобновлена позже.

Это позволяет корректно вытеснять даже горутины, которые выполняют tight loops без вызовов функций:

```go
package main

import (
    "fmt"
    "runtime"
    "time"
)

// До Go 1.14 этот цикл мог заблокировать поток навсегда.
// С Go 1.14+ sysmon вытеснит горутину через ~10 мс.
func busyLoop(id int, done chan struct{}) {
    for {
        select {
        case <-done:
            return
        default:
            // Бесконечный счёт — без вызовов функций
            _ = id * id
        }
    }
}

func main() {
    runtime.GOMAXPROCS(1) // Один поток — проверяем вытеснение явно

    done := make(chan struct{})
    go busyLoop(42, done)

    time.Sleep(50 * time.Millisecond)
    fmt.Println("main: всё ещё работает — планировщик вытесняет busyLoop")
    close(done)
}
```

### Точки вытеснения

| Механизм | Версия | Описание |
|---|---|---|
| Вызов функции | <1.14 | Пролог функции проверяет флаг preempt |
| Асинхронный сигнал | ≥1.14 | `SIGURG` вытесняет любую горутину |
| Системный вызов | все | `M` отсоединяется от `P` автоматически |

## Создание горутин

### `go func()` — базовый синтаксис

```go
package main

import (
    "fmt"
    "sync"
)

func main() {
    var wg sync.WaitGroup

    // Именованная функция
    wg.Add(1)
    go sayHello(&wg, "мир")

    // Анонимная функция-замыкание
    msg := "горутина"
    wg.Add(1)
    go func() {
        defer wg.Done()
        fmt.Println("Привет из", msg)
    }()

    // Go 1.22+: переменные цикла безопасны — каждая итерация своя копия i
    for i := range 5 {
        wg.Add(1)
        go func() {
            defer wg.Done()
            fmt.Printf("итерация %d\n", i)
        }()
    }

    wg.Wait()
}

func sayHello(wg *sync.WaitGroup, name string) {
    defer wg.Done()
    fmt.Println("Привет,", name)
}
```

### `errgroup.Group.Go()` — Go 1.25 / golang.org/x/sync

Пакет `golang.org/x/sync/errgroup` предоставляет более удобный API: `wg.Go()` принимает `func() error`, а `wg.Wait()` возвращает первую ненулевую ошибку.

```go
package main

import (
    "fmt"
    "net/http"

    "golang.org/x/sync/errgroup"
)

func main() {
    var g errgroup.Group

    urls := []string{
        "https://go.dev",
        "https://pkg.go.dev",
        "https://github.com/golang/go",
    }

    for _, url := range urls {
        g.Go(func() error {
            resp, err := http.Get(url) //nolint:noctx
            if err != nil {
                return fmt.Errorf("GET %s: %w", url, err)
            }
            defer resp.Body.Close()
            fmt.Printf("%s → %d\n", url, resp.StatusCode)
            return nil
        })
    }

    if err := g.Wait(); err != nil {
        fmt.Println("ошибка:", err)
    }
}
```

`SetLimit(n)` ограничивает параллелизм — удобно как семафор:

```go
var g errgroup.Group
g.SetLimit(4) // не более 4 горутин одновременно

for i := range 20 {
    g.Go(func() error {
        processItem(i)
        return nil
    })
}
_ = g.Wait()
```

## Типичные ошибки

### 1. Goroutine Leak — горутина никогда не завершается

Самая распространённая ошибка: горутина зависает в ожидании канала, который никто никогда не закроет.

```go
// ПЛОХО: горутина висит вечно, если никто не читает ch
func leak() {
    ch := make(chan int)
    go func() {
        val := <-ch // заблокирована навсегда
        fmt.Println(val)
    }()
    // ch никто не закрывает → утечка
}

// ХОРОШО: контекст позволяет горутине завершиться
func noLeak(ctx context.Context) {
    ch := make(chan int, 1)
    go func() {
        select {
        case val := <-ch:
            fmt.Println(val)
        case <-ctx.Done():
            return // чисто завершаемся
        }
    }()
}
```

Для обнаружения утечек используйте `runtime.NumGoroutine()` в тестах или пакет `goleak`:

```go
func TestNoLeak(t *testing.T) {
    defer goleak.VerifyNone(t)
    // ... ваш тест
}
```

### 2. Race Condition — гонка данных

Несколько горутин читают и пишут одну переменную без синхронизации:

```go
// ПЛОХО: гонка! counter читается и пишется конкурентно
var counter int
var wg sync.WaitGroup
for range 1000 {
    wg.Add(1)
    go func() {
        defer wg.Done()
        counter++ // не атомарно
    }()
}
wg.Wait()
fmt.Println(counter) // неопределённый результат

// ХОРОШО: атомарная операция
var counter atomic.Int64
for range 1000 {
    wg.Add(1)
    go func() {
        defer wg.Done()
        counter.Add(1)
    }()
}
wg.Wait()
fmt.Println(counter.Load()) // всегда 1000
```

Всегда запускайте тесты и программы с флагом `-race`:

```bash
go test -race ./...
go run -race main.go
```

### 3. Запуск без синхронизации — main завершается раньше горутин

```go
// ПЛОХО: main может завершиться раньше, чем горутина напечатает что-либо
func main() {
    go fmt.Println("горутина") // может не успеть
}

// ХОРОШО: ждём завершения
func main() {
    var wg sync.WaitGroup
    wg.Add(1)
    go func() {
        defer wg.Done()
        fmt.Println("горутина")
    }()
    wg.Wait()
}
```

### 4. Захват переменной цикла (до Go 1.22)

В Go 1.22 это поведение исправлено: переменная цикла `for i := range n` создаётся заново на каждой итерации. Если вы поддерживаете старые версии Go — явно передавайте переменную в аргументах:

```go
// Безопасно в Go 1.22+ (текущее поведение):
for i := range 5 {
    go func() {
        fmt.Println(i) // каждая горутина видит свой i
    }()
}

// Явная передача — безопасно в любой версии Go:
for i := range 5 {
    go func(n int) {
        fmt.Println(n)
    }(i)
}
```

## Вопросы для самопроверки

1. **Чем горутина отличается от потока ОС по расходу памяти и накладным расходам на переключение контекста?**
   Горутина начинается со стека 2–8 КБ (против ~1–8 МБ у потока ОС) и переключается в user space без syscall, что на порядки дешевле.

2. **Объясните модель GMP. Что произойдёт с `P`, если `M` заблокируется в syscall?**
   `M` отсоединяется от `P`; рантайм создаёт (или пробуждает) новый `M` и передаёт ему `P` — работа не останавливается.

3. **Что такое work stealing и зачем он нужен?**
   Когда LRQ одного `P` опустела, он крадёт половину LRQ другого `P`. Это выравнивает нагрузку и не даёт процессорам простаивать.

4. **Почему до Go 1.14 горутина могла «заморозить» поток, а сейчас нет?**
   До 1.14 планировщик был кооперативным — горутина уступала управление только в точках кооперации. С 1.14 появилось асинхронное вытеснение через `SIGURG`: `sysmon` принудительно вытесняет горутины, работающие дольше 10 мс, даже если в них нет ни одного вызова функции.
