# Сети и Линукс

Сетевое программирование и базовые знания Linux — область, которую проверяют на собеседованиях в любую команду, пишущую бэкенд на Go. HTTP-сервер, gRPC-клиент, TLS-рукопожатие, диагностика задержек через `ss` и `tcpdump` — всё это требует понимания сетевого стека. Go делает работу с сетью удобной, но только тогда, когда вы понимаете, что происходит под капотом.

## Почему это важно для Go-разработчика

Go с самого начала проектировался как язык для сетевых сервисов. Пакет `net/http` из стандартной библиотеки управляет пулом соединений, keep-alive, TLS и HTTP/2 прозрачно. Но «прозрачно» не значит «без настройки»: неправильный `http.Transport`, забытый `resp.Body.Close()` или отсутствующий таймаут превращают сервис в источник проблем на нагрузке.

На собеседовании вопросы по сетям появляются в трёх форматах:
1. **Теория** — «Что происходит при вводе URL в браузер?», «Зачем нужен TIME_WAIT?», «В чём разница между HTTP/2 и HTTP/3?»
2. **Диагностика** — «Как найти утечку соединений?», «Что показывает `netstat -s`?»
3. **Практика** — «Реализуйте HTTPS-сервер с взаимной аутентификацией (mTLS)», «Настройте ретрай с экспоненциальным бэкоффом».

Понимание всех четырёх слоёв этого раздела — HTTP, TCP/IP, TLS и проектирования API — позволяет уверенно ответить на любой из этих вопросов.

## HTTP: протокол прикладного уровня

HTTP — основной протокол для веб-сервисов. На собеседованиях важно различать версии:

- **HTTP/1.1** — текстовый протокол, одно соединение обрабатывает одни запрос за раз (без pipelining на практике). Head-of-line blocking на уровне протокола.
- **HTTP/2** — бинарный, мультиплексирование нескольких потоков поверх одного TCP-соединения, сжатие заголовков HPACK, server push.
- **HTTP/3** — поверх QUIC (UDP), устраняет head-of-line blocking TCP, встроенное шифрование.

В Go переключение между HTTP/1.1 и HTTP/2 происходит автоматически при использовании `net/http` + TLS. HTTP/3 требует сторонней библиотеки, например `quic-go`.

```go
// HTTP/2 включается автоматически при наличии TLS
srv := &http.Server{
    Addr:         ":443",
    Handler:      mux,
    ReadTimeout:  5 * time.Second,
    WriteTimeout: 10 * time.Second,
    IdleTimeout:  120 * time.Second,
}
log.Fatal(srv.ListenAndServeTLS("cert.pem", "key.pem"))
```

Подробнее — в статье **«HTTP»**.

## TCP/IP: транспортный уровень

TCP гарантирует доставку и порядок байт. Для Go-сервисов критичны несколько механизмов:

**3-way handshake**: SYN → SYN-ACK → ACK. При создании каждого нового соединения добавляет RTT к задержке — поэтому важны keep-alive и пул соединений.

**TIME_WAIT**: после закрытия соединения порт остаётся в этом состоянии ~60 секунд (2×MSL). Массовое закрытие соединений с одного хоста (например, нагрузочное тестирование) может исчерпать эфемерные порты. Решение: включить `SO_REUSEPORT` или использовать keep-alive.

**Алгоритм Нейгла**: объединяет мелкие пакеты в один, снижая overhead. Увеличивает задержку для интерактивных протоколов — отключается через `TCP_NODELAY`.

**Управление перегрузкой**: алгоритмы CUBIC, BBR управляют окном перегрузки. Понимание slow start объясняет, почему первые запросы медленнее последующих.

Подробнее — в статье **«TCP/IP»**.

## TLS: безопасность транспорта

TLS шифрует соединение и аутентифицирует стороны. В Go это пакет `crypto/tls` — один из самых продуманных в стандартной библиотеке.

Ключевые концепции:
- **Цепочка сертификатов**: корневой CA → промежуточный CA → сертификат сервера. Браузер/клиент доверяет корневым CA.
- **TLS 1.3**: упрощённое рукопожатие (1-RTT вместо 2-RTT), только AEAD-шифрование, нет RSA key exchange.
- **mTLS**: взаимная аутентификация — сервер тоже проверяет сертификат клиента. Стандарт для internal microservices.

```go
tlsCfg := new(tls.Config{
    MinVersion: tls.VersionTLS13,
    ClientAuth: tls.RequireAndVerifyClientCert,
    ClientCAs:  certPool,
})
```

Подробнее — в статье **«TLS»**.

## Проектирование API

Выбор API-протокола влияет на производительность, удобство клиентов и операционный overhead.

- **REST** — HTTP + JSON, максимальная совместимость, легко отлаживать через curl.
- **gRPC** — Protocol Buffers + HTTP/2, типизация, стриминг, кодогенерация. Идеален для internal services.
- **GraphQL** — клиент запрашивает только нужные поля, один эндпоинт. Удобен для сложных UI-запросов.

Для публичного API с браузерными клиентами — REST. Для high-performance internal mesh — gRPC. Для flexible frontend queries — GraphQL.

Подробнее — в статье **«Проектирование API»**.

## Типичные ошибки на собеседованиях

**1. Отсутствие таймаутов.** `http.DefaultClient` не имеет таймаута. Зависший сервер-партнёр заблокирует горутину навсегда.

```go
// Плохо
resp, err := http.Get(url)

// Хорошо
client := &http.Client{Timeout: 10 * time.Second}
resp, err := client.Get(url)
```

**2. Незакрытый `resp.Body`.** Соединение не вернётся в пул, произойдёт утечка.

```go
resp, err := client.Get(url)
if err != nil {
    return err
}
defer resp.Body.Close() // обязательно
```

**3. Игнорирование кода ответа.** Статус 200 OK ≠ успех для всех API. Всегда проверяйте `resp.StatusCode`.

**4. Хранение `*http.Client` как локальной переменной.** Каждый вызов создаёт новый Transport и не переиспользует соединения. `http.Client` должен быть синглтоном или полем структуры.

**5. Неправильная конфигурация TLS.** `InsecureSkipVerify: true` в продакшн-коде — частая находка на code review. Никогда не отключайте верификацию сертификатов в production.

## Linux-инструменты для диагностики

Go-разработчики деплоят сервисы на Linux, поэтому базовое владение сетевыми утилитами — ожидаемый навык:

| Команда | Что показывает |
|---------|----------------|
| `ss -tnp` | TCP-соединения + процессы |
| `ss -s` | сводная статистика (TIME_WAIT count и т.д.) |
| `netstat -s` | счётчики ошибок TCP/IP |
| `tcpdump -i any port 8080` | перехват пакетов |
| `curl -v --http2` | HTTP/2 negotiation |
| `openssl s_client -connect host:443` | TLS-рукопожатие вручную |
| `strace -e trace=network` | системные вызовы сети |

## Что дальше

Эта статья — обзор. Каждая тема разбирается подробно:

- **HTTP** — версии протокола, структура сообщений, keep-alive, мультиплексирование, HPACK.
- **TCP/IP** — handshake, TIME_WAIT, Nagle, congestion control, модель OSI.
- **TLS** — рукопожатие, сертификаты, mTLS, `crypto/tls` в Go, Let's Encrypt.
- **Проектирование API** — REST, gRPC, GraphQL, protobuf, версионирование, пагинация.

Рекомендуемый порядок изучения: TCP/IP → HTTP → TLS → API Design. Понимание нижних уровней делает верхние очевидными.
